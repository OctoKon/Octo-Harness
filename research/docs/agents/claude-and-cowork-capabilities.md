# Claude, Claude Code, and Cowork: capability boundary and Splyce gates

**Research snapshot: 2026-10-25.** This is a selected official-product reading of major Claude offerings relevant to a coding-agent harness. It is neither a market ranking nor an assertion that every account, region, plan, operating system, or rollout has every feature. Every Splyce runtime result in this chapter is **n=0**. Source IDs refer to [claude-product-sources.json](../evidence/claude-product-sources.json).

**Splyce deployment ruling.** Claude/Cowork hosted execution and hosted memory/state remain behavioral references only: Splyce's agent loop, execution, memory, and stored state stay local. Generation, extraction, embedding, and reranking may use an explicitly authorized per-role cloud API profile with recorded endpoint, model/revision, and egress scope; no provider/fallback is silent. A user-authorized web tool remains a separately receipted action and does not authorize unrelated corpus/state transmission.

## Cowork: what is beyond Claude Code

Cowork is best treated as the product layer that coordinates broader task work across the Claude app, not merely a GUI for the Claude Code terminal. It extends the coding-agent pattern in four material directions:

1. **Cross-surface task continuity.** A task can start, be steered, reviewed, and resumed on Desktop, web, or mobile. The cloud task can continue without local reach, while Desktop acts as the bridge when a task needs selected local folders, local MCP, browser, or computer use. [CC-08]
2. **General-work capability composition.** Cowork joins connectors, skills, plugins, browser work, local files, artifacts, projects, and recurring schedules. Plugins combine skills, connectors, and subagents; their hooks/subagents are Cowork-specific. [CC-07, CC-12]
3. **Vendor-operated orchestration.** The schedules, remote connectors, cloud sessions, account portability, connector directory, and artifact hosting are Anthropic service functions. They are excluded from Splyce; only their user-facing behavioral contracts inform a local implementation. [CC-06–CC-10, CC-14]
4. **Broader effect surface.** A Cowork task can read/write external work services, browse, work on local files, and potentially control the computer. The documented permission modes therefore have a wider impact than an edit-only CLI mode. [CC-07, CC-15]

For Splyce, that means the useful target is not a cloned app surface. The useful target is one Pi-native brain with an explicit **local capability plane**: typed local executor identities (`pi-tool`, local filesystem, local browser, local computer, local MCP adapter), a pre-effect policy gate, a durable local effect ledger, and recovery that represents unknown completion as `uncertain`. A user-authorized web fetch is a constrained external tool result, not a remote executor. Cowork’s documented breadth increases the number of effect classes to qualify; it does not remove the need to qualify them.

## Implementation order and non-claims

1. Qualify the Pi-native action/receipt seam and nested-action denial first.
2. Add explicit local filesystem/terminal executor policy and recovery.
3. Add local browser, then local connector/MCP adapters with distinct credentials and egress manifests; preserve an explicit, per-fetch authorization path for public web access only.
4. Add scheduler, artifacts, office/document skills, and child-session orchestration only after their lower-layer receipts and deletion/recovery fixtures pass.
5. Treat computer control as a separate high-trust local executor; reject cloud delegation and hosted fallbacks rather than treating either as a side effect of browser or MCP enablement.

This reading does **not** establish Claude/Cowork feature parity for Splyce, model quality, total cost, all-plan availability, product rankings, benchmark outcomes, security effectiveness, or the behavior of unlisted Claude services. It also deliberately does not restate detailed terminal/IDE mechanics already catalogued in [terminal agents](terminal-agents.md), [IDE and platforms](ide-and-platforms.md), and the [competitive mechanism review](competitive-mechanism-review.md). All Splyce gates remain proposed and **n=0** until exercised through a loaded Pi/user entrypoint with retained artifacts.
