# Streaming, documents and resource budgets

**2026-10-26; proposed implementation choices and measurements, n=0.** The base must read ordinary agent output, source and changes without Monaco/LSP. An editor is not a prerequisite for trustworthy code review. The renderer projects ordered authoritative events; it never becomes a second session journal or drops durable history to make scrolling fast.

The [markdown-it safety guidance](https://github.com/markdown-it/markdown-it/blob/master/docs/safety.md) distinguishes disabling source HTML from using an external sanitizer when HTML is enabled, and warns that plugins can affect output. Prefer explicit HTML-off plus a narrowly allowed token-to-DOM mapping for the chosen subset; do not create a new Markdown parser. Do not pass raw provider/plugin/file HTML directly to Svelte `{@html}`. If integration uses generated HTML, its escaping/sanitization boundary needs separate tests before rendering. The parser's [MIT license](https://github.com/markdown-it/markdown-it/blob/master/LICENSE) was inspected on a moving branch; implementation pin, dependency notices and exact configuration remain unqualified. FUI-26–27.

## Streaming strategy: identity before decoration

Use the existing ordered IPC stream with stable session/turn/action IDs and event cursor. Separate authoritative event ingestion from visible presentation scheduling. Coalesce text paint work within a measured frame/batch budget, but preserve event ordering and never coalesce distinct approval/outcome identities into one guessed state. A background or minimized window can reduce animation/render frequency without losing acknowledged events.

The smallest proposed renderer keeps completed turn blocks stable and renders the active incomplete tail as plain text. Incomplete Markdown fences/links/tables are not grounds to invent valid markup or executable tool arguments. Finalization parses the completed block and checks visual/selection stability. If plain-tail readability is insufficient in actual tasks, compare partial-tail parsing; do not assume a “streaming Markdown” dependency is necessary.

This is a conservative tradeoff: formatting appears later, and a very large single turn may still be costly at finalization. Test finalization with large code/tables, not just tiny token chunks. If it blocks the UI, parse off the main thread or divide qualified stable blocks with revision-aware caching; cache invalidation must account for Markdown constructs whose meaning changes with later text. Do not casually finalize every newline as an independent Markdown document.

| Proposed stream fixture                                  | Required user-visible invariant                                                | Instrumented failure signal                                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Interleaved text and two tool calls                      | Stable cards retain tool/call identity; partial arguments labelled pending     | Card becomes another call, an incomplete request appears executed, or text moves between turns |
| Split Unicode and repeated/out-of-order transport events | Text reconstructed by contract; duplicate durable event not duplicated in UI   | Replacement characters, duplicated action, wrong cursor or stale view mutation                 |
| User scrolls up/selects text while output arrives        | Scroll anchor and selection remain; explicit “new output” returns to tail      | Forced scroll, selection cleared, or keyboard focus moved by rendering                         |
| Partial fence/link then disconnect                       | Original partial output remains readable with disconnected status              | Unclosed markup hides cancel/outcome or rich parse error erases output                         |
| Cancel/late event/reconnect                              | Requested cancel differs from confirmed outcome; recovery uses snapshot/cursor | Late result overwrites another turn or retry replays an uncertain effect                       |
| Hidden/minimized then restored                           | Recover exact event projection; announce one meaningful status change          | Queue overflow drops receipts or replay floods the screen reader                               |

Use a separate restrained live region for status transitions and user-requested progress summaries. The transcript should remain readable in normal document mode; announcing every token or replacing the whole transcript in a live region prevents useful reading. A pending approval needs clear discoverability without repeated modal focus theft.

## Huge timelines: pagination before mandatory virtualization

Start with a bounded **rendered page/window**, stable message IDs and explicit load older/newer or jump-to-turn controls, while full history remains in the engine store. This is a presentation window, not a semantic history/agent cap. Search/export must operate over the admitted full scope, with unavailable data explicit. Keep the selected/focused message mounted until the user leaves it; do not recycle a node into a different action under focus.

[TanStack Virtual](https://github.com/TanStack/virtual) is a headless multi-framework candidate with Svelte support and an inspected [MIT license](https://github.com/TanStack/virtual/blob/main/LICENSE). Consider it only if measured page/window rendering fails large-history interaction budgets. It manages virtual layout, not transcript correctness, find-in-page, full-history selection, screen-reader navigation or durable storage. Exact Svelte 5 adapter compatibility must be tested at the selected pin. FUI-28–29.

[WAI-ARIA's feed pattern](https://www.w3.org/WAI/ARIA/apg/patterns/feed/) defines a specific interoperability agreement for loading articles while assistive technology reads. It is not a magic role to add to a recycled list. FUI-30. Keep ordinary section/article/list semantics initially; use feed only if its loading/focus/position contract and actual Narrator behavior are deliberately implemented and tested.

| Strategy                        | Benefit hypothesis                                          | Cost / failure risk                                                                                        | Qualification decision                                                             |
| ------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| All history mounted             | Native selection and browser find across mounted content    | Growing DOM/layout/memory; huge transcript can block input                                                 | Diagnostic baseline for representative sizes, not assumed release strategy         |
| Explicit paged history          | Small predictable DOM, clear boundary and keyboard controls | Search and copy across pages need explicit product affordances; load can disrupt anchors                   | **Minimum candidate**; preserve turn location, load failures and full-scope export |
| Virtualized dynamic-height list | Lower mounted DOM across long history                       | Height changes from code/images, focus recycling, reading cursor, selection, browser find and anchor drift | Conditional candidate only after paired performance and accessibility tests        |

Do not auto-detect a screen reader to hide a broken main experience. If a user-selectable reading view is useful, it must expose equivalent history/actions and clear paging/search; it cannot become an unsupported second product. Virtualization is rejected if resource savings require removing accessible evidence or changing history semantics.

## Proposed budgets and measurement protocol

These are **candidate engineering targets**, not measured product performance, hardware promises or release gates already approved by owners. Freeze the workload, supported Windows cell, exact dependency/build bytes, run count and acceptance thresholds before qualification. Do not tune thresholds after seeing an unfavorable candidate result.

| Metric                      | Proposed target / budget policy                                                                                                                                                  | Measurement and caveat                                                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Local action feedback       | p95 at or below 100 ms for visible pending feedback; p95 at or below 200 ms for local navigation/controls                                                                        | Input timestamp to visible paint in installed app under stream load; acknowledgement/outcome latency measured separately |
| Active stream display delay | p95 at or below 100 ms from received event to visible text when window foregrounded                                                                                              | Timestamp IPC receipt and paint; provider generation/network latency excluded and separately reported                    |
| Renderer work               | No repeated main-thread tasks over 50 ms in the representative typing/scroll/stream workload                                                                                     | Inspect traces and attribution; this is a diagnostic target, not proof of complete responsiveness                        |
| Startup                     | Record cold/warm launch to interactive unconfigured/base-only workspace; treat the first baseline as exploratory, then freeze the numerical ceiling before any qualification run | Include Rust/WebView/engine startup and provider readiness separately; a splash screen is not usable startup             |
| Bundle / installed bytes    | Zero unselected Monaco/LSP/highlighter-language/model assets; report raw/compressed JS/CSS and actual installed-byte manifest                                                    | No invented universal KB ceiling; source map/dev files and WebView provisioning reported separately                      |
| Memory / CPU                | Record whole process tree idle/stream/review peaks; no sustained memory growth after repeated session cycles                                                                     | Distinguish private bytes/working set, caches and shared WebView costs; do not sum misleading process columns            |
| Idle / shutdown             | No unsolicited network fetch, optional worker or continuous decorative animation in base-only idle                                                                               | Observe process/network/CPU traces; cleanup survives errors, external user services remain untouched                     |
| Large-history quality floor | No lost output, action identity, focus/selection or inaccessible history at stress sizes                                                                                         | Correctness and a11y gates must pass before comparing speed/resource use                                                 |

[web.dev's INP guidance](https://web.dev/articles/optimize-inp) describes responsiveness and main-thread/rendering causes; its web metric is useful context, not a desktop release certificate or a substitute for this installed-app experiment. FUI-31. The numerical proposals above are local targets; no source is presented as proving Splyce will meet them.

Proposed fixtures should include 100, 1,000 and 10,000 turns; long-path/code/diff cases; many interleaved actions; a single unusually large output; and a controlled burst source faster than rendering. These are benchmark points, not runtime limits. Keep exact Unicode/text bytes and event schedules in versioned fixtures, with integrity counts/hashes independent of the renderer. Include failed loads, disconnected history and insufficient memory/disk.

Compare plain rendering, completed-block Markdown and any virtualization/highlighting candidate with identical release build, fixture, display scale and machine. Proposed initial sampling: ten cold launches, ten warm launches and at least twenty repeat interaction/stream trials per cell, reporting sample count, median, p95, worst case and errors. Small-sample percentiles are descriptive, not robust population guarantees. Record CPU, RAM, Windows/WebView2 version, display configuration, power state, optional modules and model locality. No telemetry or benchmark upload is implicit.

Resource work must count Rust, WebView2, engine and optional processes; a smaller frontend bundle alone cannot establish a lightweight application. Failure to meet an early target triggers diagnosis and design revision, not hidden event truncation, reduced history semantics or a weaker verification/approval UI.
