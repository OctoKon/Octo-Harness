# Components and Windows accessibility

**2026-10-26; candidate selection and proposed acceptance, n=0 installed tests.** Retain Svelte 5/strict TypeScript/Vite 8 and Tauri 2. Use existing Svelte reactivity and the [desktop contract](../design/desktop-application.md); no new global-state system or parallel authority. The minimum justified component strategy is semantic HTML plus one family of qualified headless primitives for interactions that are difficult to implement correctly.

## Source availability and license boundaries

Public source is available for the candidates. Fetched license files show MIT for [Bits UI](https://github.com/huntabyte/bits-ui/blob/main/LICENSE), [shadcn-svelte](https://github.com/huntabyte/shadcn-svelte/blob/main/LICENSE.md), [historical Melt UI repository](https://github.com/melt-ui/melt-ui/blob/develop/LICENSE) and [Monaco](https://github.com/microsoft/monaco-editor/blob/main/LICENSE.txt). Those moving-branch anchors are **not selected source pins or a transitive license clearance**. FUI-12–15.

The re-review resolves the next-route identity separately: [melt-ui/next-gen at `3450a91`](https://github.com/melt-ui/next-gen/blob/3450a91f47c1c7392c5c9385c12b3d4897e85ffe/packages/melt/package.json) identifies `melt` 0.44.0 with Svelte peer `^5.30.1`; its pinned LICENSE is MIT. [Bits UI at `33186c8`](https://github.com/huntabyte/bits-ui/blob/33186c8cc7bb3e0fb8b665063fa29663b606c416/packages/bits-ui/package.json) identifies 2.20.2 with Svelte peer `^5.33.0` and MIT metadata. Both have other dependency/peer requirements. These immutable source observations resolve identity and minimum-version evidence, not the selected build pins or Windows compatibility. TD-11 must lock the complete compatible closure before reuse; the historical Melt repository cannot stand for the next package. FUI-36–38.

Before reuse, record exact component/package revision, license/notice files, all required dependencies and local modifications. Preserve applicable notices in distribution. No legal compatibility opinion is established here. Fluent guidelines and competitor feature documentation do not establish a license to copy proprietary desktop assets, branding or artwork. The engine's open-source availability is a different layer from the desktop product design.

## Splyce tokens and readable density

[Fluent's design-token model](https://fluent2.microsoft.design/design-tokens) separates raw values from semantic aliases. Reuse that mechanism conceptually: a small CSS-custom-property map for surface, raised surface, body/muted text, border, focus, selection, danger and pending state. Keep light/dark/system choices consistent across ordinary UI, code and optional editors. FUI-16.

Proposed initial design scale: 4/8/12/16/24/32 px spacing; body around 14–16 CSS px with comfortable line height, smaller metadata only when it remains readable, and headings differentiated by hierarchy rather than enormous display text. Use a Windows system UI font stack and system monospace fallback, with no mandatory font download. These are design starting points, not certified contrast or final fixed values. Test at enlarged text before freezing.

Use flat reading surfaces with subtle elevation/border or tonal separation. Muted labels must still meet contrast; semantic state includes text/icon shape as well as color. No visual animation can be the only busy indicator. FUI-10's Fluent source is guidance; Splyce's WCAG AA target must be checked on the actual selected palette and rendered controls.

Purposeful transitions should generally be 120–200 ms and never exceed 500 ms. A reduced-motion preference removes scrolling/moving transitions and shimmer; static progress text remains. Do not animate every stream token, reorder focused controls or run decorative particles behind code. This is a resource and accessibility decision, not evidence that a motion library is required.

## Keyboard, composition and focus contract

Microsoft's [keyboard guidance](https://learn.microsoft.com/en-us/windows/apps/develop/input/keyboard-interactions) treats keyboard use as a primary Windows interaction mode. Preserve conventional text editing, selection and system shortcuts. Every mouse action has a labelled keyboard route; pointer-only context menus are insufficient. FUI-17.

| Area / fixture            | Proposed exact action and expected result                                                                                                     | Must not occur                                                                                                        |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Main landmarks            | Tab/Shift+Tab traverse visible controls in understandable order; navigate between rail, task, composer and review via labelled affordances    | Hidden panes receiving focus, focus entering inert background or giant transcript tab sequences                       |
| Composer                  | Plain textarea retains normal Enter/newline; explicit Send and proposed Ctrl+Enter submit only outside active composition                     | Enter used to confirm an IME candidate submitting the prompt; AltGr/text-editing keys intercepted globally            |
| Composition               | Japanese/Chinese IME candidate selection, Korean composition and focus changes preserve text; use composition state and test real event order | Treating every keydown as an instruction; rejecting non-Latin input; synthetic events presented as physical IME proof |
| Approval dialog           | Initial focus on a safe meaningful control; Tab stays in modal; Escape/close does not approve; close restores focus                           | Default Enter approving changed/expired request or focus returning to an absent DOM node                              |
| Combobox                  | Type search, arrows, select, Escape; visible active option matches accessible active state                                                    | Focus leaving to an unrelated pane on streamed updates; displayed choice confused with effective model                |
| Pane resize / narrow view | Keyboard route to resize or choose practical layout; focus stays on the same logical task/control                                             | Drag-only panel management or clipping the deny/cancel action                                                         |
| Optional Monaco           | Reach editor, discover focus mode and leave with documented Tab-focus behavior; preserve external controls                                    | Keyboard trap or assuming Monaco's editor screen-reader support certifies surrounding dialogs/diff navigation         |

[UI Events](https://w3c.github.io/uievents/#dom-keyboardevent-iscomposing) defines keyboard composition state; implementation must qualify Windows IME behavior in the packaged app rather than assuming one boolean is a complete cross-browser fix. Shortcut defaults remain proposals for TD-02; show them in help and button tooltips, respect application scope, and avoid unsolicited global hotkeys. FUI-18.

## Accessibility matrix beyond a compiler

Microsoft's [Windows best practices](https://learn.microsoft.com/en-us/windows/apps/get-started/best-practices) call for keyboard operation, accurate accessibility information, contrast-theme testing and text/display scaling. The tests below are proposed TD-54/R1 evidence, all **n=0**. FUI-19.

| Dimension                | Minimum proposed Windows evidence                                                                                       | Failure that blocks the related claim                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Narrator / UI Automation | Read landmarks, session status, composer, approval scope, tool results and diff file/hunks in reading/focus modes       | Status missing or repeated per token; controls unnamed; selected state only visual; a pending approval cannot be found     |
| High DPI / text size     | 100/125/150/200% display scaling, enlarged text to 200%, move between mixed-DPI monitors; record actual supported cells | Cropped labels, wrong native-dialog placement, unreadable target, inaccessible close/cancel, coordinate-dependent approval |
| Zoom / reflow            | Resize and zoom to narrow content; ordinary prose/forms reflow; code/diff has its own labelled horizontal scroll        | Whole-window horizontal scrolling hides primary action or transcript order changes                                         |
| Contrast themes          | Actual Windows contrast theme, focus/selection/error/diff plus/minus retained without decorative colors                 | Shadow-only boundaries disappear; selection or focus vanishes; color-only meaning                                          |
| Reduced motion           | OS animation/reduced-motion on; no sliding panels, animated auto-scroll or pulsing-only progress                        | Activity becomes invisible when animation stops; perpetual decorative timers consume resources                             |
| RTL / mixed direction    | Arabic/Hebrew message, Latin code/path, mixed punctuation and long identifiers; copy exact source order                 | Visually reordered target misleading approval; mirrored code contents or corrupted copy/export                             |
| Input alternatives       | Keyboard, pointer, touch where supported, clipboard multiline paste and OS on-screen keyboard                           | Hover-only details, tiny undiscoverable controls, focus lost during keyboard appearance                                    |

[Media Queries 5](https://www.w3.org/TR/mediaqueries-5/#prefers-reduced-motion) and [CSS Color Adjustment](https://www.w3.org/TR/css-color-adjust-1/#forced-colors-mode) define preference/forced-color mechanisms; these specifications are not proof of a particular WebView2 build's behavior. Avoid blanket `forced-color-adjust: none`; use system-color-compatible outlines and retain native semantics. [W3C direction guidance](https://www.w3.org/International/questions/qa-html-dir) supports explicit direction handling: use logical layout properties and appropriate `dir`/isolation for message content, with code/path presentation tested separately. FUI-20–22.

Do not claim WCAG conformance from a static linter, vendor statement, one screenshot or simulated media query. Automated checks catch regressions; manual Windows Narrator, real IME and system-theme checks cover a different layer. Font fallback, portal focus, text scaling propagation and mixed-DPI transitions remain material unresolved risks until the packaged application exists.
