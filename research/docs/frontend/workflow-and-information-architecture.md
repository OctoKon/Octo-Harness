# Workflow and information architecture

**2026-10-26; proposals, with installed Splyce results n=0.** The user-selected direction is a Codex-led workbench with complementary Claude interaction discipline. Public product behavior informs task organization, not a copied shell, brand, artwork or implementation. The engine selection remains separate from this frontend proposal.

## What the references actually establish

OpenAI's February 2026 [Codex app introduction](https://openai.com/index/introducing-the-codex-app/) describes project-organized agent threads, reviewing changes in a thread, commenting on diffs and worktrees. The current [Worktrees guide](https://learn.chatgpt.com/docs/environments/git-worktrees) distinguishes managed and permanent environments, handoff and recoverable cleanup. These support a workspace/task/review hierarchy. They do not make worktrees a security boundary or establish a required Splyce cleanup policy. FUI-01–02.

Current [Codex troubleshooting](https://learn.chatgpt.com/docs/reference/troubleshooting) explicitly distinguishes the project's Git changes from the agent's last-turn changes. This is important counterevidence to an apparently simple “changes” number: a review pane may contain somebody else's work. Splyce must label the comparison and provenance instead of implying all visible changes were produced by the selected task. FUI-03.

Anthropic's [Desktop documentation](https://code.claude.com/docs/en/desktop) documents file-by-file diff review, line feedback submitted together and panes that can be resized or moved. Its [interactive-mode reference](https://code.claude.com/docs/en/interactive-mode) exposes deliberate multiline composition and transcript inspection. Reuse the interaction lessons: clear input ownership, review before another action and readable progressive detail. Terminal keybindings and the vendor's full pane system are not a Windows GUI specification. FUI-04–05.

These are product-documentation observations. Documentation does not prove usability, performance, Narrator support or current installed layout. “Professional” and “elegant” are proposed qualities to test through task completion, discoverability and recovery, not measured competitor rankings.

## One primary hierarchy

The proposed navigation hierarchy is **workspace → session/task → turn/action → evidence**. A workspace is a filesystem/environment identity; a session is conversation ancestry and execution state; a turn contains correlated tool calls and outcomes. Do not collapse these concepts into one tab title. The [provider/session contract](../design/providers-profiles-and-sessions.md) owns durable identities, writer ownership and transition semantics.

| Region          | Minimum content and default behavior                                                                                         | Avoid / optional                                                                       | Acceptance action                                                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Navigation rail | Workspace groups, searchable session list, selected session, readable activity/unread status; keyboard-accessible new task   | Recursive tree widget without real nesting; many dashboard tiles; mandatory RAG search | Reopen selected session after refresh; stable selection by ID despite duplicate titles; ordinary search works without optional services |
| Task header     | Task title, workspace/environment, branch or snapshot when available, run state; details disclosure                          | Branding displacing target identity; status represented only by an animated dot        | Long workspace/title remains inspectable; target is readable before submit, approval or apply                                           |
| Conversation    | User input, assistant text, correlated tool/action summaries, visible outcome and evidence links                             | Every event becoming a toast; tool JSON crowding ordinary reading                      | Interleaved calls retain identity; expand/copy action details using keyboard without moving the composer                                |
| Composer        | Labelled multiline text area, attachments/context summary, explicit send, cancel while running, effective model/role context | Unrequested rich-text editor; automatic execution of dropped content                   | Draft survives switching away/back; invalid/unavailable state explains why send cannot proceed; composition never sends accidentally    |
| Context pane    | Changes, files or evidence for the selected task with comparison/snapshot identity                                           | Full IDE, terminal grid, universal draggable docking                                   | Closing returns focus to its opener; changing comparison announces label and preserves understandable selection                         |
| Settings/setup  | Base-only setup, provider profiles and optional modules; requested/effective states                                          | Empty module dashboards, implicit installs or brand-based provider readiness           | Skip setup is valid; absent module explains an explicit install action without fetching/importing it                                    |

At wide sizes, conversation and review can coexist. At constrained width, switch between task and review using labelled controls; opening review must preserve draft, scroll anchor and selected diff hunk. Width thresholds follow measured readable content and 200% text scaling, not device marketing categories. Desktop window resizing and zoom are V1 obligations; a phone product is not implied.

## Original visual direction

Propose a quiet technical workbench: warm neutral surfaces in light mode, charcoal surfaces in dark mode, one restrained blue-green accent for selection/action, and explicit textual status. Use subtle surface separation, modest radii and a strong reading column rather than repeated floating cards. These are Splyce proposals, not sampled competitor tokens. The [component chapter](components-and-windows-accessibility.md) specifies token roles, accessibility and motion limits.

Reserve accent emphasis for the current task, actionable request and active comparison. Use a clear title/body/caption hierarchy; provenance and failure text remain ordinary readable text. Tool cards show a compact action verb, target, state and disclosure, with full arguments available for review. Count labels must say what they count: changed files, pending approvals or unread outcomes. A count alone cannot imply success or importance.

Claude's visible pane model provides useful progressive disclosure, but unrestricted docking adds persistence, focus, resize and restore obligations. Keep two stable content regions initially. Codex's many-project model makes task switching useful, but hidden activity can obscure an outstanding approval. A persistent pending-action indicator should navigate to the exact request without approving it or stealing focus.

## State/action contract

The following are proposed UI fixture assertions for TD-02/06 and existing journey owners, not additional backend schema or task allocation. All transitions use admitted commands and authoritative responses. Optimistic presentation may show pending intent; it cannot invent effect completion.

| Starting state                      | User action                     | Required visible next state                                                                       | Failure / recovery assertion                                                                                                              |
| ----------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| First launch, no provider           | Continue base-only / skip       | Usable navigation/settings; composer explains unconfigured generation                             | No model download, hosted login or optional package starts; configuring a provider returns to the saved task draft                        |
| Ready, valid draft                  | Send once                       | Accepted/pending state correlated to the new turn, then running only on acknowledgement           | Repeated click cannot create an unlabelled duplicate; rejection retains text/attachments; unavailable connection is not replaced silently |
| Running                             | Edit draft / navigate elsewhere | Current run continues visibly; next draft stays separate                                          | Editing text does not mutate submitted input or active approval arguments                                                                 |
| Running                             | Cancel                          | Cancel requested, then confirmed canceled, failed or uncertain                                    | A click is not proof the process stopped; late text stays attributable; further effects remain engine-fenced                              |
| Running with selected model A       | Select model B                  | Choice of next-turn or explicit cancel-and-switch; effective A remains displayed until transition | Failed switch leaves the real effective binding readable, retains draft and explains corrective action                                    |
| Interrupted/disconnected            | Reconnect                       | Recovering with last durable cursor/snapshot; safe navigation and draft remain                    | No automatic resubmission or replay of effects; unresolved action stays uncertain with evidence                                           |
| Stored session                      | Resume                          | Workspace/profile/connection readiness inspection and writer availability                         | Changed workspace or missing provider blocks execution with specific repair action; viewing history stays possible                        |
| Selected turn                       | Fork here                       | Explicit ancestry/fork point and new session identity                                             | Source session and files remain unchanged; files/worktree creation is a separate, explicit operation                                      |
| Review based on snapshot S          | Apply selected change           | Applying only after current admitted approval and snapshot check                                  | A stale comparison disables apply, explains why and offers refresh; refreshing does not silently discard review comments                  |
| Pending approval                    | Deny, close or lose engine      | Request inert/denied/expired according to engine outcome                                          | Reconnect cannot revive a stale approve button; focus returns to request origin or meaningful task control                                |
| Completed turn with no verification | Open outcome                    | Unverified result with evidence and available verification action                                 | Never render a generic green “done” that erases verification, truncation or cleanup uncertainty                                           |

Provider switching must distinguish saved defaults, session overrides, per-role selection and current effective model. A menu of brand names is insufficient: readiness, local/cloud destination, unavailable capabilities and requested/effective revision matter. Do not expose credentials in form summaries or errors. Scope and draft retention follow [providers/profiles/sessions](../design/providers-profiles-and-sessions.md), not a second renderer-owned configuration store.

## Focused composer and command discovery

TD-71's context chips are removable references to explicitly selected files/context, not hidden upload consent or proof that the provider received the content. A chip exposes readable name, source/scope, availability and remove action. Resolving or submitting it follows the admitted engine path; missing/stale files retain the draft and explain repair. Pasting text stays text. Navigating between sessions cannot transfer attachments or draft contents to the wrong task; any local draft persistence follows the existing data/privacy contract rather than an ad hoc renderer database.

TD-73's command palette should index the application's existing named actions and navigation, with current task/workspace scope visible. It is a discoverability surface, not a shell prompt or new dispatch system. The proposed keyboard opener is application-scoped and must be qualified against text editing/IME conflicts. Search presents a labelled empty state, unavailable commands explain why, Escape restores the exact opener and selection invokes the same admitted action as its ordinary control. Privileged operations still require current approval; search results cannot bypass confirmation, manufacture permission or silently change workspace. TD-77 supplies only the static shortcut reference.

Composer serialization reads `HTMLTextAreaElement.value`, the API value normalized by the textarea to U+000A LF line breaks. Use that same representation for draft persistence and provider submission; presentation wrapping must not insert submitted line breaks. Preserve non-line-break whitespace, combining characters, supplementary characters and intended line boundaries across CRLF/CR/LF paste. Do not promise clipboard byte identity or silently normalize Unicode to another canonical form. Original file attachments and source artifacts keep their own byte digests independently of text-entry normalization. [WHATWG textarea semantics](https://html.spec.whatwg.org/multipage/form-elements.html#the-textarea-element), FUI-35.

## Review and recovery without false reassurance

Label diff source explicitly: working tree, staged, branch comparison or task snapshot only when that comparison exists in the engine contract. Display file path and hunk location independently of narration. Binary/large/unavailable content gets a meaningful status and safe open/export choice; lack of a rendered diff is not “no changes.” User comments remain bound to the reviewed revision; a newer snapshot can make them stale.

Recovery should retain what the user needs to decide: submitted intent, partial output, acknowledged effects, uncertainty and the next safe action. Retry is offered only where the engine exposes a qualified idempotent or reconciled action. “Try again” must not hide the possibility that an external effect already happened. The [trust and qualification chapter](trust-failure-and-packaged-qualification.md) specifies the negative and packaged tests.

## Limits and counterevidence

Neither reference guarantees that Splyce's multi-provider session histories are portable. A familiar model picker cannot make incompatible tool/content histories valid. A worktree provides separate files, not sandboxing, zero conflicts on integration or cheap disk use. A visually dense professional workspace can increase cognitive cost and keyboard distance; test the smallest base-only journey before adding panels.

No proprietary desktop code, screenshots, icons, exact tokens or trade dress are imported here. Open-source engine availability is a separate question from rights to a branded desktop design. Candidate dependencies require their actual pinned license/notice records before code reuse. Public feature descriptions establish comparison evidence, not permission to copy assets or a universal “best frontend” conclusion.
