# Trust, failure and packaged qualification

**2026-10-26; proposed gates, all runtime samples n=0.** The GUI presents and requests actions; privileged commands, policy checks, provider egress and durable outcomes remain in the existing shell/engine contracts. An attractive interface cannot make an uncertain effect safe, prove a provider compatible or grant a preview native privileges.

## Renderer and preview boundaries

[Tauri capabilities](https://tauri.app/security/capabilities/) associate permissions with windows/webviews and document that multiple capabilities merge permissions. Remote API access is configurable rather than impossible. Registered `invoke_handler` application commands are allowed across app windows/webviews by default unless explicitly enrolled through `tauri_build::AppManifest::commands` and permission configuration. Splyce must enroll every privileged custom command, grant it only to intended callers, keep unprivileged local webviews and untrusted previews outside those permissions, validate named commands in privileged code and avoid generic shell/filesystem/process passthrough. Capability declarations do not sandbox trusted Rust/engine/plugin code. FUI-32.

| Content / entrypoint                   | Minimal proposed presentation                                                                | Authority / acceptance boundary                                                                                                 |
| -------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Model/tool/plugin Markdown             | Escaped text or qualified Markdown subset                                                    | No execution or grant from rendered instructions; original source retained for copy/evidence                                    |
| Code and diffs                         | Inert selectable text, snapshot/file identity and explicit user actions                      | Copy/open/apply are separate admitted actions; highlighted HTML does not become trusted source                                  |
| Links                                  | Show destination and use qualified scheme/target handling                                    | No implicit provider request, custom-protocol execution or broad filesystem opening; engine/shell owns admission                |
| Images and remote references           | Base placeholder with source/size/unavailable state; explicit admitted fetch if supported    | Reading a transcript must not contact third-party trackers, load arbitrary local paths or obtain provider credentials           |
| HTML/SVG/other active documents        | Base source view or explicit safe external-open route; no active document preview by default | Any future live preview gets a dedicated threat model, origin/capability partition, navigation restrictions and installed tests |
| Local dev preview                      | Optional selected capability, if shipped; distinguish project server from trusted app assets | A localhost address is not trusted merely because local; unrelated service/native privileges remain unreachable                 |
| Drag/drop, imported session, deep link | Inspect requested target/action and validate schema/scope                                    | Presence of content never auto-submits prompt, runs instructions, installs a module or expands a grant                          |

Treat links, images, parser plugins and syntax-highlighter output as distinct trust boundaries. CSP is defense in depth; it does not replace encoding, safe URL handling, permission checks or restricted IPC. Native file open/export must use the existing scoped path handling and platform dialog route. Diagnostic errors are redacted before renderer/export sinks, not merely hidden by collapsed UI.

No exploit examples, private content, internal locations or vulnerability instructions are needed in this public design. Negative tests should keep sensitive fixture detail in appropriately controlled test material and expose only safe case identifiers and expected denial/results in public reports.

## Failure actions must match what is known

| Visible condition                             | Display and allowed recovery                                                  | Incorrect behavior to reject                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Provider unconfigured / unavailable           | Role/connection readiness, specific configure/retry route and preserved draft | Silent fallback, auto-login or automatic model download                                     |
| Authentication / quota / unsupported protocol | Distinct redacted cause and relevant settings/help action                     | Generic “network issue,” credential in stack trace or zero usage inferred from missing data |
| Engine disconnected                           | Last confirmed state, reconnect pending and retained output/draft             | Spinning forever, enabling stale approval or resending last task automatically              |
| Action canceled / cancel requested            | Different labels and actual acknowledgement/outcome                           | Cancel click immediately shown as successfully stopped                                      |
| Tool effect uncertain                         | Evidence and reconciliation route provided by engine; no generic retry        | “Failed, try again” that may repeat an external side effect                                 |
| Stale review / approval                       | Inert action, current identity mismatch and refresh/re-request route          | Approving by old dialog position, stale file range or mismatched profile revision           |
| Persistence / disk failure                    | Unsaved/unacknowledged state and safe export/repair if available              | Claiming turn safely saved or deletion complete before durable acknowledgement              |
| Module draining / cleanup failed              | Owner/dependency/effective state and incomplete cleanup visible               | Marking off/uninstalled while tools still admit work; deleting user-managed services        |
| Unknown usage / verification                  | Unknown/unverified text and available evidence                                | Zero cost, passed verification or green completion invented from absence                    |

Keep failure explanations concise, with expandable redacted technical detail and copyable correlation identifiers where useful. A tooltip cannot be the sole explanation for disabled send/apply. Restore focus to a meaningful control when a modal/action fails; retain input and selection unless the user explicitly discards it. Error handling is part of the main design rather than a toast added after the happy path.

## Real Windows test layers

Tauri's current [WebDriver guidance](https://tauri.app/develop/tests/webdriver/) recommends WebdriverIO with `@wdio/tauri-service`; the embedded provider and external `tauri-driver` are distinct routes. Embedded operation uses test plugins; external `tauri-driver` supports Windows/Linux and needs the Windows driver route qualified. The same page distinguishes browser-only frontend mode with mocked IPC. Do not treat browser-only output as native evidence. FUI-33.

The [locked desktop stack](../foundations/desktop-stack-decision.md) selects the Windows embedded route for qualification; TD-06/11/34 implement that decision, not an independent external-driver preference. An external route needs a recorded failing gate or approved same-contract alternative. Pin the actual compatible toolchain. Record test/release artifact hashes and configuration differences; an instrumented pass alone cannot qualify the release. The uninstrumented release must pass security/lifecycle smoke and its actual desktop journey through a qualified non-embedded automation or manual path before advertisement. Test automation/debug plugins, broad execute helpers and mock-command authority must not ship enabled in release.

| Layer                                                 | What it can establish                                                                           | What it cannot establish                                                                           |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Type/Svelte/lint                                      | Types, template diagnostics and consistent source                                               | Runtime message validity, correct authorization or accessible real dialogs                         |
| Component/browser fixtures                            | Deterministic states, event projection, focus logic, malicious/malformed-content denial         | Windows packaging, native dialogs, OS theme propagation, real IME/Narrator or actual child cleanup |
| Packaged Windows app + deterministic engine transport | Full shell/UI event/failure/recovery paths, installed assets and accessibility on recorded cell | Real provider wire compatibility or model behavior from a fake transport                           |
| Packaged Windows app + actual engine/store/workspace  | Admission, effects, persistence, crash/reconnect, source verification and process ownership     | Other Windows architectures, providers or devices not actually exercised                           |
| Authorized actual local/cloud provider                | Exact provider/model/config stream/cancel/history/error behavior                                | Universal provider/API compatibility or untested model features                                    |

Record exact app/engine/schema/build identities, fixture revision, commands, expected assertions, pass/fail counts, environment and artifact digests. Native tests require actual installed/loaded entrypoints, not `vite dev` with a mocked bridge. Provider/device support needs its own actual-service evidence. Report n=0, skipped, unsupported and unknown distinctly.

For docs-only changes, runtime E2E is N/A because no runtime behavior changes. Run the repository documentation checks, verify local links/source JSON and review the publication diff. This research does not qualify an installed app or authorize a runtime PR without its applicable gates.

Rejected evidence shortcuts: search snippets alone; secondary summaries when primary pages were available; old public Markdown mirrors as canonical vendor docs; repository popularity as compatibility/performance proof; React-specific examples as Svelte APIs. An attempted markdown-it `docs/security.md` URL returned 404; discovery resolved the actual `docs/safety.md`, which was fetched. Sources not used for selection still matter as counterevidence: Shiki explicitly warns that lazy grammar imports can remain in distributed bytes; Monaco documents a Tab trapping mode; WAI-ARIA feed requires a genuine interaction contract; Codex documents review content from outside the agent's changes. Each complicates an attractive shortcut. The minimum solution reduces scope while preserving those obligations.

Next research is conditional on concrete failures: a Bits primitive that fails packaged focus/IME/Narrator tests can trigger a bounded Melt/native alternative trial; a measured history bottleneck can trigger TanStack qualification; a demonstrated code-reading need can trigger Shiki or optional editor trials. No additional library or pane is justified merely by a competitor feature list. Source pins, tests and measurements remain open; **all runtime qualifications are n=0**.
