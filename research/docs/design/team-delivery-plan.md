# Nine-person research-to-build delivery plan

**Planning artifact, reconciled 2026-10-26; implementation and runtime evidence n=0.** This assigns the complete current roadmap as 70 bounded tasks; it does not authorize building the runtime now or claim the work exists. [Master plan](../../../MASTER-PLAN.md) owns product/package gates. The latest decisions are a proper lightweight Windows-only V1 desktop GUI, a barebones Splyce-owned Pi-derived headless-engine fork, independently selected modules, local application state and explicitly permitted local/cloud inference. The desktop supersedes the earlier CLI/TUI client plan; a terminal embedded in a window is not the product. Optional research candidates are not all mandatory dependencies. A task qualifies its named mechanism; replacing a candidate needs a recorded same-contract decision, not additional speculative scaffolding.

Every task's first cell gives its qualitative difficulty and a short risk reason. These are routing judgments, not measured effort, deadlines or a promise that D3 work is risk-free. A task that exposes a D5 authority gap stops at the reviewed shared boundary and returns that gap to Itachi rather than silently expanding its owner's remit.

Every task follows [AGENTS.md](../../../AGENTS.md) and [CONTRIBUTING.md](../../../CONTRIBUTING.md), including **Ponytail ultra**, no work on `main`, and a branch prefixed with the contributor's exact GitHub username, for example `ShlokShah01/TD-12-session-list`. Keep an already assigned shared checkout on its current branch; separate contributors use their own checkout/branch and preserve others' work. Before opening **any** PR, run applicable local end-to-end checks to **PASS** on the actual candidate and record evidence. A missing runner, unavailable necessary endpoint or failing E2E is not a waived gate: complete the test setup/fix or keep the work local. PRs use concise bullets covering the full change scope, tests with observed results, and material risks. No task grants direct-main, self-approval, force-push or premature PR permission.

**Review rule:** `B` means backend review by `Itachi-1824`; `U` means mandatory UI/UX review and test evidence by `MdSiddiqx`; `BU` needs both domains. Authors cannot approve themselves. When either lead authors, the other lead provides independent code-owner review while the owning lead records domain/test evidence; a backend specialist or frontend peer may assist without replacing the lead gate. This matches AGENTS/CONTRIBUTING and the two-lead CODEOWNERS list. Disputed scope goes to the user; author green reports alone never close a task.

All user-facing UI is a desktop GUI. The locked planning stack is **Tauri 2 + Svelte 5 + strict TypeScript + Vite 8**, with a thin Rust desktop shell supervising the Splyce-owned Pi-derived TypeScript core on packaged **Node 24 LTS**. Exact compatible patch versions/lockfiles are validated-build gates; the stack choice is not runtime evidence. Follow the [desktop stack decision](../foundations/desktop-stack-decision.md) and [desktop application contract](desktop-application.md); source/packaging/Windows architecture support still need qualification. V1 supports Windows only; Linux/macOS are future research/port questions, not advertised V1 cells. Base file/task/diff views are accessible plain text. Monaco is a separately installed optional editor module, with no editor/LSP/RAG/model payload in base. Splyce owns and modifies the Pi-derived engine core by default; it is not limited to an outer plugin/wrapper or a fork only after hook failure. Keep one existing Pi-derived TypeScript/Node loop, not a Rust port or a second agent loop. Follow the [core fusion and upstream patch map](core-fusion.md). Native webview screens, dialogs and controls implement the product; no terminal renderer is embedded as a substitute GUI.

The desktop IPC bridge maps qualified SDK/RPC operations of the Splyce-owned Pi fork to shared Splyce contracts; compatibility is verified against the fork revision actually shipped. Rust owns only the reviewed window/IPC/process/capability boundary; the Node engine owns policy, receipts and session/model behavior. The renderer has no independent grant authority, generic shell/filesystem access or credential store. TD-07 gives Itachi the native engine/core-hook patch map plus the hard Rust shell/process/trust boundary, TD-15 gives lapsecoder the engine IPC protocol, and TD-08 gives MdSiddiqx the renderer/client state adapter. TD-27 gives dnarsh complex module orchestration through those shared ports. No new task IDs, agent loop or duplicate operational store are introduced.

GUI acceptance requires real packaged-webview automation, screenshots for relevant states, mouse/keyboard navigation, focus restoration/trapping, accessible names, contrast/color-independent status, resize/high-DPI behavior, understandable error/retry/cancel flows and actual platform accessibility evidence where claimed. A browser-only component test, Pi RPC result or terminal screenshot is useful lower-level evidence, never proof of the desktop user journey. Headless contracts remain diagnostic/integration surfaces rather than the product UI.

## Shared files and task execution contract

TD-01 is the sole owner of shared record/schema versions and fixtures under planned `packages/splyce-pi/src/contracts.ts` and `tests/fixtures/contracts/`. TD-02–06 prepare bounded proposals without editing that shared file; TD-01 reconciles them and freezes version 1 before implementation branches use it. Later schema changes return to TD-01's owner and both domain reviewers if client semantics change. TD-26 owns configuration transition code, TD-15 owns receipt ordering, TD-28 owns installed package records, and TD-10 owns Pi ancestry mapping; their contracts reference the shared schema rather than creating independent authorities.

Paths below are **planned**, not present files. Unqualified `src/` paths mean `packages/splyce-pi/src/`; desktop frontend lives under `apps/desktop/src/{components,routes,stores,lib}`, Rust shell/IPC/lifecycle under `apps/desktop/src-tauri/`, and real webview automation under `apps/desktop/tests/gui/`. `tests/` paths are repository-relative unless an optional package is named. A parent task retains integration ownership while workers use separate symbols/files or serial handoffs; shared-file edits do not run concurrently. `src/` modules describe Splyce-owned responsibilities and may live inside the Pi fork according to [core fusion](core-fusion.md); their names do not authorize a parallel wrapper authority. The owned fork is planned at `vendor/pi/`, preserving upstream paths. `Pi core:` means `vendor/pi/packages/coding-agent/src/core/`; `Pi agent:` means `vendor/pi/packages/agent/src/`; `Pi API:` means `vendor/pi/packages/ai/src/api/`. `packages/splyce-pi/src/` owns shared contracts/native imports/desktop bridge, not a separate wrapper authority. TD-11 pins the actual source checkout/build layout. Admission, egress, receipt acknowledgement, verification and selection fences are wired into actual engine dispatch/context/persistence paths before effects or sensitive writes; an extension wrapper alone cannot certify them. API-specific changes modify qualified native Pi transports rather than inventing a competing provider engine. Do not precreate empty modules from this table. Planned optional screen paths do not authorize bundling every feature into the base: I1/R1 must inventory frontend assets as well as engine packages, and separately selected UI contributions follow the reviewed local module/trust contract. Dynamic import of an already shipped optional implementation is not selective installation. Reuse Pi and installed dependencies before introducing an abstraction. No human-team concurrency cap is specified; an agent-session concurrency limit is unrelated to nine-person task ownership.

Core edits have explicit serial handoffs. TD-07/Itachi owns the engine patch map and native interception invariants. TD-15/lapsecoder owns receipt/IPC integration against those reviewed core boundaries. TD-13/14/16/26/31/32/40/47/50 remain Itachi-owned policy, credentials, concurrency, deletion and verification authority. TD-19–23 transport owners patch the actual Pi API implementations under that shared egress contract; TD-39 consumes the native optional-memory port rather than making an extension authoritative. All participants touching the same core symbol hand off the current fork revision and regression before another task edits it. TD-11 records upstream base pin, owned fork source/branch and final built fork revision; upstream changes trigger rebase plus the same core/GUI regression suite, not a silent vendor update.

Each task receives its named fixture/input, produces code or a reviewable contract plus evidence, and hands off its changed paths/symbols, caller wiring, exact passing checks, evidence artifacts and unresolved failures to the named domain lead before dependent integration. It records final upstream base/owned-fork source pins, exact executed commands, observed outputs, artifact references, privacy checks and unresolved limits in the [qualification register](qualification-register.md). Current runnable documentation checks remain `npm run format:check`, `npm run lint:markdown`, `npm run check:docs` and `npm run test:docs`. ## Waves, critical path and completion

1. **Contract wave:** TD-02–06 can proceed independently as proposals; TD-01 reconciles/finalizes them. TD-07 proves the native Pi-core patch boundaries and Rust shell/process/IPC trust before any foundation claim. TD-08 and TD-11 can then qualify desktop client/build surfaces while TD-09 establishes the real store. Each person can read their task's linked research and prepare synthetic fixtures without editing another owner's schema.
2. **Core wave:** TD-09 → TD-10/15 → TD-13/14 → TD-24/25/26 establishes truthful effects/recovery. TD-16 plus the shared protocol contract unlocks independently owned API bindings TD-19–23. TD-12/18/30/34/36/55/56/57 can consume frozen event fixtures while backend work progresses; fixture renderer state and backend/RPC results are not packaged desktop GUI proof.
3. **Setup/session wave:** TD-27 → TD-28 → TD-29/37 proves selective installation. TD-31 → TD-32 → TD-33/35 proves actual session/model behavior. Desktop integration revisits real engine failures, backpressure/reconnect and native-window behavior, not only fixture screenshots. TD-42 depends on TD-47's real verification receipts.
4. **Release wave:** TD-50/51/52 and TD-54 close independent security/recovery/provider/UI acceptance. TD-58 is the actual Windows-only packaged-desktop release gate and whole-stack lightweight measurement; TD-59 documents observed GUI paths. No optional-memory/LSP success can substitute for zero-extra-payload base proof. No GUI screenshot can substitute for backend/effect evidence, and no RPC/terminal success can substitute for GUI E2E.
5. **Optional wave:** TD-39–41/44 can qualify selected Phase 2 modules after their named core dependencies. TD-43/45/48/49/61–70 require the stable base where stated.
