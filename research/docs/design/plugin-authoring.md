# User-created plugins and local builds

**Status: proposed, unimplemented; plugin/build/lifecycle qualification n=0.** Users can create features in their own local builds, load their own local packages, or install compatible packages from a custom Git source. No marketplace listing, central approval, paid account or mandatory publisher signature is required for an explicit user-trusted local plugin. The base remains barebones; plugin install and activation follow the [module contract](modular-installation.md). Providers follow the [profile/API contract](providers-profiles-and-sessions.md).

Reuse Pi's real extension/resource APIs and package manifest, documented in the [package source audit](../foundations/pi-package-installation.md) and [pinned source contracts](../foundations/pi-source-contracts.md). Add only the Splyce-owned effect/state/lifecycle bindings that Pi cannot provide. Do not invent a competing plugin engine, second model loop or new MCP client. Exact exported SDK names/version are chosen from the qualified implementation; the responsibilities below are proposed contracts, not callable APIs today.

## What a plugin can add

| Extension surface                    | Owner / integration                                                    | Boundary                                                                                                                                                                          |
| ------------------------------------ | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tools and commands                   | Pi registration with Splyce admission/receipts around declared effects | Namespaced IDs, versioned input/output schema, scoped targets, cancellation and typed failures; partial/unvalidated model arguments cannot dispatch.                              |
| Provider/model protocols             | Qualified Pi provider extension plus C4 operation bindings             | Declares wire API, actual modalities/tool/schema limits, credentials/egress and stream/cancel/usage behavior; no automatic fallback or ambient account use.                       |
| Memory/context backends              | Optional installed adapter over cited-source/projection ports          | Derived indexes never become authority. Scope, freshness, correction, source epochs, deletion and rebuild contracts apply.                                                        |
| LSP/browser/device/document adapters | Selected runtime package and explicit driver/model closure             | Own processes/files/connections and cleanup; no SDK/driver/model download on ordinary startup or enable.                                                                          |
| Skills/prompts/themes/UI resources   | Pi's supported resource loader and client-specific extension surface   | Instructions cannot widen grants; headless support is declared separately, and off resources do not remain advertised. No new UI framework is needed to load an instruction pack. |
| Analysis/scheduling/workflows        | Optional local job integration using existing state and ownership      | Advice cannot grant permissions or mark work verified. No hidden independent autonomous loop or unbounded background worker.                                                      |

Plugins may depend on other selected packages. Their complete dependency closure and executable setup are part of the user's reviewed install plan; choosing a source does not approve every future moving revision. Custom local source may be uncommitted: record source/build-content digest and dirty snapshot rather than pretend a Git commit certifies it. Custom Git sources use immutable resolved revisions and actual loaded-byte checks. Source import does not transfer ownership of the user's original files.

## Minimum package and lifecycle contract

| Concern                | Required information / behavior                                                                                                               | Proposed acceptance case                                                                                                                                    |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity/compatibility | Plugin ID/version, source/build digest, Pi/Splyce API range, declared client/OS/architecture, license/notice and dependency/resource manifest | `P1_custom_plugin_compat`: incompatible API/version and duplicate tool/resource identity fail before load; no existing package overwritten.                 |
| Discovery/trust        | Parse metadata as data; explicit user selection/trust precedes executable loading                                                             | `I1_custom_plugin_source`: user-trusted local and custom Git packages can be installed without a marketplace/signing gate; unselected resources never load. |
| Initialization         | Side-effect-free metadata discovery; explicit activation gets owned context and declared resources                                            | `P1_plugin_start_failure`: failed initialization removes partial registrations/resources and stays failed, not half-enabled.                                |
| Effects/state          | Use the same current-grant/effect/receipt path and namespaced local state/artifact inventory; no secondary authoritative journal              | `P1_plugin_effects`: denied nested effect leaves target unchanged; state write failure cannot become success.                                               |
| Configuration          | Versioned validated plugin-owned keys with explicit defaults; no override of core policy, credentials or another namespace                    | `P1_plugin_config`: unknown required schema or collision fails atomically, preserving the old active state.                                                 |
| Reload/update          | Fence dispatch, drain/cancel owned work, settle receipts, close old registrations, then bind the new exact version once                       | `P1_plugin_reload`: active call plus repeated reload creates neither duplicate tool/job nor late old-version output.                                        |
| Data migration         | Versioned schema, validated source/data inventory, backup/export and tested compatible rollback or explicit refusal                           | `P1_plugin_migration`: failed migration leaves prior readable data or a recoverable blocked state; no silent destructive downgrade.                         |
| Disable/uninstall      | Remove exposure and owned runtime references; preserve unrelated shared files/services and retained data                                      | `I1_custom_plugin_remove`: code absence, no new dispatch/orphan, user source survives, retained data remains exportable/deletable.                          |
| Failure/reporting      | Typed start/runtime/cancel/cleanup error and plugin/version identity; redact credentials/content before external sinks                        | `P1_plugin_failure`: exceptions/timeouts stay attributable without secret output or fake completion.                                                        |

Pi extensions run as trusted in-process code with the host's OS authority. Tool hooks cannot contain arbitrary direct filesystem, process or network operations in such code. Installing user-created code is allowed, but must not be advertised as a sandbox or as fully audited effect coverage. Declared effects routed through Splyce get receipts; direct operations outside that path remain outside the enforcement guarantee. An untrusted-plugin isolation claim requires a separately qualified process/container/WASM execution boundary with narrow interfaces and lifecycle tests; it is not a prerequisite to an explicit trusted local plugin build, and cannot be manufactured by a permission checkbox.

## Desktop compatibility

V1 is the Windows desktop GUI. Pi terminal widgets/themes are not automatically desktop components. Backend tool/provider resources and GUI resources qualify separately; an incompatible terminal-only presentation reports unsupported instead of embedding a TUI. Desktop panels use the reviewed typed command/event/view contract or an explicit trusted local frontend build, with CSP/capability and lifecycle tests. Installing backend code cannot silently import arbitrary renderer scripts. The [desktop contract](desktop-application.md) owns actual GUI rendering and packaged-app evidence.

## Development and release path

Ship one minimal documented example when P1/I1 is implemented: a local package with one namespaced tool, validated input/output, one scoped artifact and deterministic cleanup. Include a second opt-in provider example only when its real protocol adapter exists. Pin the example's host/API versions and source; install it through the same user path, not an internal test-only loader. Test interactive and supported headless registration, denial, reload, crash/restart and removal against the loaded Pi host. Removing registration, validation, admission or cleanup must make these tests fail.

Local development uses the selected local package source and explicit rebuild/reload, with source/build digests in receipts. No automatic watched-code execution is enabled in the base. A user may explicitly opt into a development watcher; file changes cannot mutate code in the middle of an admitted call. A local build can include the user's chosen modules, while its build manifest records the exact closure and terms; that build does not establish the official base footprint or upstream support.

P1 owns resource/API compatibility and runtime wiring; I1 owns acquisition/build/install ownership and staged version changes; C2/C3 own effect/receipt boundaries; R1 owns installed examples and compatibility evidence. Required evidence includes source/build/host pins, package/import/installed-byte manifest, actual entrypoint, commands, receipt artifacts, negative cases, cleanup and unrun limits. Published plugin capability is limited to its observed platform/client/provider cells. The source repository's `.skills/` development rules do not imply every skill is packaged in the user application.
