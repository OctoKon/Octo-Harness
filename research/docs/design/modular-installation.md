# Barebones installation and optional modules

**Status: proposed, unimplemented; installation, runtime and footprint results n=0.** This is the current user requirement and supersedes earlier proposals that enabled memory or other extras on a fresh profile. It complements [model choice](user-controlled-models.md), [feature controls](capability-map.md) and [R1/I1 in the master plan](../../../MASTER-PLAN.md).

The default installation contains the selected Pi host, the minimum Splyce policy/operational-receipt/verification integration, and its required runtime dependencies. Existing file/search/edit/terminal tools provide the basic coding path. Ordinary source search is not a background RAG index. Core operational receipts and Pi's own session history do not activate cross-session memory capture or retrieval. Installing the host does not download model weights.

**No optional modules are bundled, fetched, installed, loaded or enabled by default:** cross-session memory, RAG/vector/graph indexes, embedding/reranking models, LSP/language servers, skill packs, external MCP servers, browser/desktop/mobile drivers, OCR/audio/vision extras, decision/forecast models, delegation workers or optimizers. Inventory upstream code in the pinned Pi distribution: an empty checkbox cannot make bundled optional code/native assets disappear. Qualify a minimal distribution through upstream packaging/resource seams or the smallest justified packaging patch; extra built-ins cannot be excused as barebones merely because disabled. If pruning cannot meet the measured installed-payload contract, F0 records that limitation and compares another existing base under identical gates. No tree-shaking, isolation or zero-dependency claim is established yet.

## Setup and later changes

Setup offers **continue with the base only** as the default. Users can select modules immediately or add them later through the same interactive/headless path. Skipping setup remains a valid installation; a missing generation model is shown as unconfigured until the user selects a compatible local or cloud service, or explicitly provisions local weights. No ambient credential, hosted login, fallback or unsolicited download makes that state appear ready; cloud setup is an explicit user selection, with its own role/data policy.

Fetching an extension is acquisition of trusted executable code, not a sandbox. A Git URL, signed archive or repository popularity does not establish code safety or authorize network/process/filesystem use. Package trust and runtime grants are separate; arbitrary unreviewed modules cannot be described as contained by Pi tool hooks. Reuse reviewed Pi seams; do not build a second package ecosystem, agent loop or generic dependency language just to represent this install plan.

## User-created plugins

Users can author local packages, install their own Git sources and include selected plugins in personal local builds without marketplace approval. [Plugin-authoring contracts](plugin-authoring.md) map actual Pi resource/API reuse, source/build identities, trusted-code limits, namespaced effects/state, compatibility, reload, data migration and installed-example tests. Explicit custom local source is supported; no default ambient discovery, automatic setup execution or expansion of grants follows.

## Planned package boundaries

Core planned code lives in `packages/splyce-pi/src/`; its dependency/import graph excludes optional implementations. `packages/splyce-memory/src/` owns optional receipt-backed capture/summary/lexical memory, with no mandatory dense/graph/model dependency. `packages/splyce-lsp/src/` owns the optional LSP client; selected language-server assets are separate explicit dependencies. Dense, sparse, graph and rerank backends each declare their own installable adapter/dependency closure; browser/device/document and decision/forecast adapters follow the same rule. These are planned build boundaries, not a demand to create empty packages or one framework per toggle. Split by actual dependency/asset ownership; do not duplicate shared small code or ship every backend in one optional mega-package.

Pi's inspected Git package identity is repository-based, and its installer clones a repository plus package dependencies. A monorepo with resource filters alone does not establish independently fetched module payloads or concurrent per-module versions. **Selected official distribution path:** produce one independently packed artifact per installable module/dependency unit in the source repository release pipeline, bound to the full Git commit and artifact digest. I1 fetches only the user-selected artifact set plus its explicitly accepted lock-resolved closure, stages/verifies it, then hands the installed local package/resource manifest to Pi. Do not use Pi's whole-monorepo Git clone as the official selective installer. Custom single-package Git sources and local development folders remain explicit user choices with their actual fetch/install cost disclosed; no per-repository multi-version promise. A provider-host-independent selective Git-tree adapter is a future alternative only if this artifact path fails a concrete requirement, not an undecided first-release fork. It must inspect actual bytes, lock/dependency closure and startup checkout identity; Git pins alone do not freeze transitive dependencies. No new general package manager is authorized by this missing seam.

## Component, setting, state and data are different

Track the minimum distinct facts needed by the existing store: **not installed / staging / installed / failed** package state, the immutable installed revision, requested feature configuration, effective runtime state and owned artifact/dependency references. The package record and configuration transition have recoverable intent/outcome ordering; activation cannot observe partially installed bytes. Disabling a feature does not uninstall it. Uninstalling a module cannot leave its tools advertised or jobs newly admitted. Installing a module does not enable another module to satisfy a dependency silently.

Before installation, a known optional key can be shown as not installed with an install action; unknown keys still fail validation. Dormant module data remains accessible through the base's minimal ownership/export/delete inventory even after code removal. The uninstall plan must either complete requested deletion using qualified cleanup before removing code or retain a qualified cleanup path; it must not strand private data behind an absent plugin. Do not retain the full optional runtime merely to support a deletion claim. Interrupted work, pending jobs and migrations stay blocked/reconcilable until their original contract is available; reinstall never blindly replays effects.

| Profile / module              | Initial state and dependency rule                                                                                                                                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Barebones host                | Installed; no optional module/model/index/server files. Minimal policy, receipts, verification and Pi conversation recovery work without RAG/LSP.                                                                                          |
| Native memory                 | Not installed/off. User chooses capture/summaries/lexical recall; no embedder or graph dependency unless separately selected by the accepted plan. No retroactive ingestion of sessions captured while off without explicit authorization. |
| Dense/sparse/graph/rerank     | Separate optional selections; manifest declares real storage/encoder/extractor dependencies. Exact source-backed baseline remains available only if installed/enabled.                                                                     |
| Code intelligence             | LSP module and chosen language servers are optional downloads. Built-in ordinary file/search tools remain usable when no server is installed.                                                                                              |
| MCP / skill resources         | Reuse Pi transport/resource APIs; install/load only approved selected server packages or skill packs. Built-in transport code is not proof that optional servers or skill libraries were installed.                                        |
| Browser / devices / documents | Selected adapter plus explicit driver/runtime/model dependencies only. No browser engine, OCR model or device SDK in the base by default.                                                                                                  |
| Decision / forecast           | Optional adapter plus user-selected compatible local model or permitted cloud API. Selecting Timestral or another checkpoint does not enable a scheduler or install other analysis models.                                                 |

Repository development skills under `.skills/` govern agents working on this source repository; their presence in Git does not require shipping/loading the entire library in the user application. Research/docs are likewise separate from installed runtime payloads. Measure package/archive contents, unpacked dependency closure, model/native bytes and idle resources separately; demand-loading an already bundled optional dependency does not satisfy selective installation.

Fixture packages are test inputs loaded by the actual manager, not a mocked manager or extra base payload. TD-58 requires base absence, manager fixtures and actual app upgrade/uninstall evidence.
