# Brutal gap audit

**What this repo does:** Splyce is a researched plan for a Windows desktop coding application over a fused Pi-derived core. The base has no optional RAG/LSP/editor/model payloads; users choose local/cloud providers and custom modules. This audit assumes concurrent desktop/session/profile changes under one local authoritative store. Reconciled **2026-10-26**; runtime and installed-app results remain **n=0**.

## Must-fix findings and specification disposition

1. **Conflicting cloud rules — repaired.** An approved cloud profile previously could not collect required live-provider evidence because other chapters prohibited it. The master and Claude/Codex comparisons now separate explicit cloud trials from strict all-local profiles and excluded hosted execution/storage. Exact-provider qualification remains TD-14/50/52, not a claimed run.
2. **The client and engine strategy drifted — repaired.** Earlier terminal/extension-only directions conflicted with the final Windows GUI and authorized native core fusion. The [desktop contract](desktop-application.md), [locked stack](../foundations/desktop-stack-decision.md), [native patch map](core-fusion.md), master and 70-task plan now share one execution/authority map. Pi headless interfaces are internal, not a substitute user interface.
3. **Resume/install/switch records could not reproduce state — repaired.** A restart after selecting the same model ID on another provider or activating a Git module lacked immutable identity. [Record contracts](implementation-contracts.md#record-contract) now include provider/binding/profile revisions, selection/config transitions, installed-package ownership and session writer fencing. TD-01/09/15/26/28/31 must implement and test them before dependent behavior closes.
4. **Disabled packages were mistaken for absent bytes — decision repaired.** Pi can resolve/install packages before resource filters and discover ambient resources. [Selective installation](modular-installation.md#planned-package-boundaries) now chooses independently packed per-module artifacts bound to Git revision/digest and accepted dependency closure, handed to Pi as installed local packages. Base-only/existing-config, integrity and byte/import/process inventories are mandatory I1/R1 tests. Packaging is still unimplemented, not a measured footprint win.
5. **Trusted plugins could be mistaken for contained code — claim repaired.** A user-created in-process extension can perform operations outside routed APIs. [Plugin authoring](plugin-authoring.md) explicitly permits trusted local/custom Git builds and limits enforcement claims to qualified native paths; arbitrary-code containment needs its own isolated executor evidence. No permission checkbox or Tauri renderer capability claims to sandbox trusted engine code.
6. **Cloud cancellation/retention lacked a source-backed per-cell contract — documentary gap repaired.** Local cancellation/deletion cannot establish provider-side acknowledgement or erased inputs. [Lifecycle research](../capabilities/cloud-inference-lifecycle.md) adds eight primary-source records, account/model/API distinctions and explicit operation/retention/cancel evidence fields. Unknown remote behavior remains unknown; a data class requiring a stronger guarantee is denied. TD-50/52 and GUI states must preserve this distinction.

## Build gates, not hidden research omissions

The first real proof remains one packaged Windows GUI using the same fused engine, store, profile, policy and verifier through permitted edit, denial, interrupt, resume/fork and model switch. Removing the native admission gate or durable commit must fail it. Optional module tests, provider tests and browser component tests cannot substitute for this path. These are explicit tasks and release gates; no runtime was built or exercised during this research phase.

The [nine-person plan](team-delivery-plan.md) assigns all 70 current tasks, difficulty, owner, reviewer, dependencies, planned paths, sources, future commands, failure criteria and handoff. Pending invitations are access dependencies, not unassigned work. Frontend starts from the locked stack and frozen contracts; hardest backend work stays with Itachi, followed by the user-specified priority. A failed/unknown required E2E blocks opening a PR; documentation-only work uses the real documentation pipeline and records runtime E2E as N/A.

## Coverage and limits

Reviewed root rules/plan/contribution flow, methodology and candidate frontier, category/evidence navigation, core/desktop/provider/module/plugin/session/memory contracts, the team graph, validator/tests and workflows. Selected source chains inspect upstream implementation and contradictory evidence. This is not a file-by-file independent audit of every donor project, every model asset or all internet candidates. [The gap journal](../agents/gap-sweep-candidates.md) records dated frontiers and reopens discovery when new eligible candidates appear; no global exhaustion or universal-best claim is made.

**Verdict:** The documented contradictions above are repaired and the current scope has an owned, staged handoff. Complexity reduces risk where one native contract replaces conflicting paths; it grows faster than risk removal if implementations create duplicate stores, loops, installers or UI state authority. The next proof is the shared core/desktop fixture before optional breadth, not more parallel wrappers.

**Not checked:** runtime/build/provider/Windows installation, resource benchmarks, actual accessibility or private account arrangements. Material risk remains unqualified native dispatch/output boundaries, packaging, cloud lifecycle and physical recovery; each has an assigned gate rather than a fabricated pass.
