# Splyce implementation contracts

**Active product scope:** Splyce is OSS with a barebones, modular local application and local authoritative state. Users explicitly select local and/or cloud inference per provider/profile/operation; a local-only profile forbids inference egress and silent fallback. Hosted execution, managed memory storage and unsolicited telemetry are not default dependencies. Current local+cloud direction supersedes the earlier global local-only ruling. [Current master plan](../../../MASTER-PLAN.md).

**Status:** proposed, unimplemented; runtime evidence **n=0**. This narrows the [master plan](../../../MASTER-PLAN.md) packages F0, J0, C1–C5, M1–M2, X1, P1 and R1 into records and observable behavior. Pi owns model turns, provider-facing generation and conversation branches. Splyce owns grants, effect receipts, verification and derived memory. These are **Splyce interfaces**, not claims about Pi's API. The pinned [Pi foundation](../foundations/pi-foundation.md) and upstream [extension types](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/extensions/types.ts) define the actual integration surface; [extension documentation](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/extensions.md) describes trusted in-process execution, branch/lifecycle hooks and nested tool calls. Recheck those sources when the Pi pin changes.

## Record contract

Every durable record has required `schemaVersion: integer`, `recordId: opaque string`, `createdAt: UTC timestamp`, `scopeId: opaque workspace/task identity` and `sourceIds: string[]`. IDs are unique within the store; references must resolve inside the caller's grant. Timestamps order observations only when accompanied by durable sequence or source revision. Unknown required schema versions fail closed on read; unknown optional fields survive read/migrate/export without creating a grant, tool or provider capability. Secret values, raw provider credentials and unrestricted absolute paths are forbidden in records. An artifact reference is checked on every read, including after cache hydration.

Session append ownership is distinct from **workspace mutation ownership (C2/J0)**. Reuse the authoritative store's lease/epoch primitive keyed by admitted canonical workspace identity, not `piSessionId`; aliases or overlapping writable roots cannot obtain independent conflicting owners. The record binds workspace, owner run/writer, epoch, input snapshot and active/draining/uncertain state. Before a mutating turn reads its editable snapshot or dispatches work, acquire that ownership; other sessions may inspect but cannot mutate the same workspace concurrently. Independent qualified worktrees have separate ownership. TD-09 supplies durable ownership, TD-13/14 enforce it in native filesystem, Git and command paths, TD-25 reconciles recovery and TD-31 transfers session ownership only after outgoing effects settle.

Every routed mutation rechecks its ownership epoch. Read-modify-write, replace, rename and remove also require the expected source/target identity or explicit expected absence, checked under that ownership immediately before mutation; a conflict requires refresh/review, never blind overwrite. Commands with possible writes hold workspace ownership until their full owned process tree settles; lease expiry/disconnect cannot prove that an old writer stopped. Crash/takeover remains blocked or uncertain until reconciliation establishes quiescence. This serializes admitted Splyce writers, not arbitrary external editors, trusted direct-OS plugin code or another uncoordinated application; platform target/race checks and that trust limit remain explicit. `C2_workspace_writer` must reject a second same-workspace writer, then reject its stale input after legitimate handoff, preserving the first result. A surviving child blocks takeover; a qualified independent worktree can proceed. No optional delegation module supplies this base guarantee.

A branch anchor is a Splyce record with `branchAnchorId`, `piSessionId`, `forkPointEntryId` and nullable `firstChildEntryId`. The latter stays pending until an actual first child exists; do not mutate an immutable record to invent one—append its resolved mapping and retain the predecessor. Pi itself exposes session/leaf/path operations, not a `branchId`. [Observed identity behavior](../foundations/pi-source-contracts.md#branch-state-and-compaction).

`sourceIds` distinguish operational evidence (run/action/outcome/artifact/Pi branch references) from documentary research IDs in the [public source ledger](../evidence/README.md). Research IDs justify design choices; they cannot certify a run. Verification receipts additionally bind exact command, exit, output artifact, verifier environment/input manifest, final Git base/HEAD and immutable `candidateSnapshotId`. The snapshot covers tracked dirty bytes and declared test-relevant untracked inputs, modes/link identities and the diff/content manifest. Recheck it before apply/completion; a matching HEAD alone cannot certify changed workspace bytes. Output-only exclusions must be declared and cannot omit verifier inputs. `verified_complete` requires successful receipts for the delivered snapshot and no uncertain actions. `C5_dirty_snapshot` mutates tracked and relevant untracked bytes without changing HEAD and must invalidate verification.

## Ports and transaction order

The proposed **Pi integration port** translates observed Pi turn, tool, branch and lifecycle events into Splyce IDs. It asks `PolicyPort.decide(action, grantSnapshot)` before any effect, then calls `ReceiptPort.commitDecision` and `commitIntent`. Only after both commits may the owned executor invoke the tool. A result or error goes through `commitOutcome` before Pi/headless clients receive a completion claim. A store failure at any pre-effect step blocks the call. A post-effect failure leaves `uncertain`, with physical-state reconciliation required before retry. The gate must cover Pi built-ins, [Pi's MCP path](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/mcp.md), nested calls and any separately authorized user shell path; a bypass blocks F0/C2.

The immutable run grant snapshot is an audit input, not continuing authority after revocation. Intersect it with current host policy and current grants immediately before dispatch, including queued, resumed, nested and delegated work. Record the effective policy revision; changed arguments or a changed grant require a new decision. Withdrawal blocks new dispatch and requests cancellation of affected in-flight work. Report any already-performed or unconfirmed effect honestly; revocation cannot undo it. C2 must test withdrawal while a call waits for approval and while a child is queued.

`MemoryPort.capture(receiptRef, piBranchRef)` consumes committed evidence; `ModelRolePort.call(operation, sourceRefs, scope, deadline)` handles derived extraction/embedding/reranking under the same egress policy; `MemoryPort.query(scope, query, grant)` returns IDs first and hydrated evidence second. These port names describe Splyce responsibilities, not upstream methods. Pi's `tool_call` blocking, `ctx.executeTool` parent identity, `getBranch()` reconstruction and `session_start`/`session_shutdown` behavior must be verified against the pinned source and real F0 fixture. Initialization and shutdown are idempotent. On restart, join Pi's active branch with receipts by stored IDs; a missing Pi node or unconfirmed nested effect stays unresolved. Pi's transcript is not the authoritative effect ledger.

J0 supplies the single actual store and `ReceiptPort` before C1/C2 use it. It qualifies durable record commits, explicit write failure, schema validation and reopen behavior. C2 admission tests inject failures into that same store. C3 extends this floor with action/effect reconciliation; it does not retroactively supply a store that C2 already claimed to qualify.

An async memory worker checkpoints a durable source cursor and an idempotency tuple (`scopeId, sourceId, extractionRevision`). It commits observation, source links and cursor in one transaction; a crash before commit retries, a crash after commit finds the tuple and does not duplicate claims. Capture → redact → extract/summary → validate citations and scope → build derived index → publish generation. Retrieval authorizes **before cache lookup** and **after source hydration**; cache keys include scope, grant revision, deletion watermark and index generation. Returned evidence IDs are recorded as supplied to the model; a claim of use requires the run to cite them. Correction appends a superseding observation. Delete commits a query-blocking tombstone first, then purges raw/projections/indexes/caches; restore from backup reapplies tombstones before serving. Failed purge is incomplete deletion, never a success receipt.

Every producer binds a source/scope deletion epoch when reading input. Publication atomically checks the current epoch and tombstones alongside the observation/artifact/index commit. Deletion advances the epoch, blocks new work, cancels/drains affected jobs and discards late results before verifying purge. An old job cannot recreate deleted content. Inventory and resolve Pi transcripts, forks, compaction summaries, active model context/KV caches and exports; no covered surviving copy may be used to restore or recapture the deleted source. If qualified source removal is unavailable, deletion remains incomplete and blocks its release claim. `M2_late_writer_delete` pauses extraction across deletion; `M2_pi_source_replay` resumes a source-bearing fork. Both inspect physical retained artifacts and every retrieval route.

## Storage and provider qualification

One store is authoritative for operational receipts; memory indexes and caches are rebuildable projections. J0 selects and qualifies the actual store before C1/C2 admission. C3 extends its qualification with effect reconciliation, migration and advertised-platform recovery tests; it does not defer initial store selection. Candidate decision inputs include the selected Node runtime's built-in SQLite support/stability, a native SQLite binding's binary and packaging burden, and a Rust sidecar's IPC, process and migration burden. Do not claim any wins or API availability without pinning and running each candidate. A sidecar cannot become a second agent loop or independent authority. Selection records license, release pin, transaction/fsync behavior, backup/restore, upgrade/downgrade and observed installed-platform results.

| Store candidate                                          | Advantage                                                     | Key cost and reversibility                                                                                                                                |
| -------------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Node built-in SQLite, if supported by the pinned runtime | One runtime and no extra native package                       | API/stability and durability behavior need direct qualification; two-way before released data.                                                            |
| Native Node SQLite binding                               | Mature synchronous transaction surface may simplify ordering  | Binary compatibility, native packaging and blocking work require platform proof; two-way before released data.                                            |
| Rust support sidecar                                     | Isolates blocking storage work and may share native libraries | IPC, second process lifetime and failure reconciliation add complexity; avoid unless measured need. Store format becomes costly to reverse after release. |

| Role operation | Retry, cancellation and stream/usage contract                                                                                                                                                                                                  |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Generate       | Retry only before any visible output or tool effect unless the provider proves safe resume. Keep text/tool deltas ordered, record actual finish reason and observed usage; cancel records provider acknowledgement separately from local stop. |
| Extract        | Validate output schema and every source citation; malformed output is failure or explicit repair attempt charged to the run. Do not infer constrained decoding from post-validation.                                                           |
| Embed          | Retry pure request only with identical model contract and scope. Reject wrong dimension, normalization or truncated-input contract; index cutover waits for complete validation.                                                               |
| Rerank         | Keep candidate IDs through scoring; record model/scoring revision and missing/NaN scores as failures. Cancellation or outage retains baseline order only as an explicitly labeled degraded route.                                              |

Every operation, including Pi generation before its first/retried request, validates selected local/cloud provider, immutable profile/binding revision, applicable transport policy, hosted-role qualification and data-class egress before dispatch, carries deadline and correlation ID, distinguishes timeout/transport/provider/schema/policy errors, and records observed versus estimated usage. Unknown provider capability fails before dispatch. [User model selection](user-controlled-models.md) binds independent role selections to exact checkpoint/content, runtime, operation and config revisions, permits compatible unbenchmarked experimental choices, and separates user-supplied terms from distributed asset rights. Switching fences stale outputs/caches/index publication; a streamed Pi turn finishes under its pinned contract or records cancellation before replacement. No implicit download, model substitution or checkpoint-triggered code execution is allowed. Commit a correlated request intent before any billable/external model dispatch; store failure blocks the request, interrupted/unknown usage remains unknown, and unsafe retries are not implied by an SDK default. Qualify each actual SDK transport/credential boundary, not one assumed global fetch hook. Failures never become zero usage, zero results or success. [Inference research](../capabilities/inference-local-and-cloud.md) describes candidate engines, not qualified adapters.

## Synthetic end-to-end proof

Fixture repository `w-demo` starts at revision `A` with a failing test and a project note saying “use lexical fallback when code intelligence is stale.” Session `s1`, branch `b1`, run `r1` captures that decision as scoped artifact `e1`. A permitted edit `a1` commits decision → intent → observed outcome, changes the fixture to revision `B` and passes exact verifier `v1` on B. Result is `verified_complete` only after `v1` and cleanup receipts are durable. A denied nested edit `a2` aimed outside `w-demo` leaves fixture bytes unchanged and records policy denial.

Close Pi, start session `s2` with empty chat context, and ask why the edit used lexical fallback. M1 observation `m1` cites `e1` and `a1`; M2 ID search expands the original evidence. The response cites `e1`, while the run records supplied evidence and source revision. A query from another workspace returns no `e1`. Delete `w-demo`: tombstone blocks queries immediately, purge removes `e1`/`m1` from all active routes, reindex and authorized backup restore keep them unavailable; a restore that cannot enforce the tombstone stays offline. This sequence is synthetic specification, not a measured result.

Proposed future integration cases under the master plan's `test:integration -- --case ID` runner: `F0_pi_interception` asserts denied ordinary/nested/MCP calls cause no effect; `C1_branch_resume` asserts no event duplication or abandoned-branch completion; `C3_crash_matrix` asserts intent without outcome is uncertain and never replayed; `C4_local_only_egress` asserts zero cloud dispatch for every role; `C5_revision_binding` asserts old verifier receipts cannot certify B; `M1_worker_restart` asserts one cited observation per idempotency tuple; `M2_scope_delete_restore` asserts canary absence after cache, rebuild and backup restore; `R1_installed_recovery` runs the whole sequence on every advertised platform. Each case saves exact fixture/base revision, command/exit, Pi and Splyce pins, receipts and observed failure state. A fake endpoint proves contract faults; real model/provider and installed-package claims need their own tests.

## Output privacy is a release blocker

The source-observed Pi result-hook error path can report an extension failure and continue. Therefore `tool_result` alone cannot certify fail-closed redaction. F0/C2 must identify and qualify a boundary covering progress updates, final `content`/`structuredContent`/`details`, errors, Pi's own persisted session, headless/export output and model-bound context. A synthetic canary must remain absent from every unauthorized sink even when the redactor fails. If a wrapper cannot enforce the ordering, record the exact minimal Pi fork patch and regression before shipping; no claim of private/offline handling may bypass this gate. [Source control flow](../foundations/pi-source-contracts.md#tool-decision-failure-and-result-projection).
