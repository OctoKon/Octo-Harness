# Pi provider and session contracts

**Reviewed 2026-10-25; pinned source inspection, runtime/API calls n=0.** Sources are official Pi at `d5b3de22d0e24a3e9c38a9410d3329b099717283`, indexed by [PST-01–PST-14](../evidence/pi-provider-session-sources.json). The current user requirement permits **local and cloud inference**, with local application execution/state, a barebones default and opt-in adapters. This supersedes earlier local-only inference proposals. The profile, egress and installation obligations below are proposed Splyce contracts, not existing Pi APIs. No provider registration or successful source reading qualifies a deployed endpoint.

## Provider identity, API family and transport

Pi distinguishes a provider identity, model ID, API implementation and endpoint. A provider name is not a wire protocol or locality guarantee. One API family can serve many vendors or a local compatible server; several API families can coexist in the same runtime. [Model configuration](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/models.md) supports provider-specific `baseUrl`, `api`, models and overrides; a custom provider extension supplies behavior beyond configured compatibility.

The exact chat-generation `KnownApi` IDs in [types.ts](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/types.ts#L64-L76) are:

| Pi API ID                 | Source-observed implementation boundary                                                                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `openai-completions`      | Chat Completions, despite the shorter ID: the adapter invokes `client.chat.completions.create`. This is not the legacy text-completions endpoint.                                     |
| `openai-responses`        | Separate Responses adapter invoking `client.responses.create`; request construction includes `store: false`. That parameter is not a guarantee of remote retention/deletion behavior. |
| `azure-openai-responses`  | Distinct Azure adapter and configuration; do not infer support from OpenAI credentials alone.                                                                                         |
| `openai-codex-responses`  | Distinct subscription/Codex adapter; not interchangeable with every API-key Responses profile.                                                                                        |
| `anthropic-messages`      | Messages adapter invokes `client.beta.messages.create`; supports endpoint and authentication-specific handling.                                                                       |
| `google-generative-ai`    | Gemini adapter invokes `client.models.generateContentStream`; rejects an injected custom `fetch` distinct from global fetch.                                                          |
| `google-vertex`           | Separate Vertex API/authentication path.                                                                                                                                              |
| `bedrock-converse-stream` | Separate AWS Bedrock streaming family.                                                                                                                                                |
| `mistral-conversations`   | Separate Mistral conversation family.                                                                                                                                                 |
| `pi-messages`             | Pi-specific family; its presence does not mean an arbitrary compatible server implements it.                                                                                          |

The first, second, fifth and sixth rows were traced into their actual [transport implementations](https://github.com/earendil-works/pi/tree/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/api). The remaining rows are source-declared distinct families, not an equal-depth transport or live compatibility audit. `Api` also permits extension strings; a string alone does not register an implementation. Separate image/classifier API types exist, so a chat adapter does not establish embedding, reranking, forecasting or every other role.

`ModelRuntime` is the coding-agent's owner of model/auth/provider orchestration. Its [stream path](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/model-runtime.ts#L660-L755) resolves the actual provider and auth, applies request endpoint/headers, normalizes context and invokes the provider's `streamSimple`. Missing provider or unresolved auth produces an explicit error. Virtual-model routing can select another model; the source strips caller credentials before a cross-provider route resolves its own. This is credential handling, not Splyce authorization of that route.

The [ModelRegistry facade](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/model-registry.ts) exposes `find(provider, modelId)`, `getAll()`, `getAvailable()` and asynchronous `refresh()`. Refresh must finish before relying on synchronous snapshot reads. Available authentication/catalog metadata is not a successful generation/tool/schema probe. [Provider composition](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/provider-composer.ts) checks extension registration and fails when a required API implementation or authentication method is missing. No universal Splyce profile API was found or assumed.

**Proposed Splyce boundary:** bind each role to an explicit provider/model/API/endpoint/runtime/config revision and egress policy. Local-only profiles reject cloud dispatch; explicitly permitted cloud roles may send only authorized data classes to their admitted endpoint. Redirection, routing, retries, summarization/compaction and delegated roles recheck that boundary. Do not infer locality from loopback/private syntax or transport compatibility. Barebones selection must not install every adapter, authenticate every provider or download models. Existing Pi-installed bytes require honest inventory rather than an unsupported claim that configuration removes them.

## Credentials and executable configuration

[Provider docs](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/providers.md) describe API keys, OAuth and ambient Bedrock/Vertex credentials. Examples of distinct provider variables are `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` and `GEMINI_API_KEY`; a compatible local service can use its own configured authentication. The model documentation orders runtime key overrides before stored credentials, configured model keys and environment/ambient credentials. Extensions may define additional authentication behavior; qualify the actual chosen path.

Pi stores selected credentials in `auth.json`. Logout removes Pi's stored credential, not provider-side access, process environment or keys supplied elsewhere. OAuth tokens/refresh, cloud ambient identity and gateway credentials are independent of model choice. Credentials belong in credential facilities or environment, never public receipts, exports or model context.

Configuration is not always inert data. In [credential resolution](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/resolve-config-value.ts), command-valued settings can execute local credential-helper processes. Stored-auth command resolution caches results, including unresolved results, for the process lifetime; model-key/header composition uses uncached request-time resolution. The [auth store](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/auth-storage.ts) and provider composer establish the differing paths. A failed helper can leave auth unavailable; model-config resolution can throw a descriptive error. Splyce must separately admit reviewed credential helpers and route them through the existing native decision/durable-intent/outcome/cleanup ordering before spawn (TD-16/50, C4_credential_helper_lifecycle). Keep raw credential output out of ordinary retained process artifacts and reject late revoked/canceled cache publication. Importing a provider profile must not execute helpers or authorize unrestricted local commands. No executable credential examples are needed in an install catalog.

Transport observability differs. The inspected OpenAI/Anthropic adapters accept custom fetch, while Gemini explicitly rejects that option. Their existing signals, payload/response hooks and terminal events are useful integration surfaces, not proof that one fetch wrapper mediates every SDK transport or trusted provider extension. Responses maps aborted/error paths to error events and rejects a stream ending without a terminal stop reason. Preserve protocol-specific partial text/tool deltas, finish reasons, cancellation and unknown usage; no outage becomes an empty successful result. Actual cloud cancellation and retention claims need provider-specific evidence.

## Live model changes need an additional fence

[`AgentSession.setModel(model, options)`](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/agent-session.ts#L2535-L2561) checks configured authentication, changes `agent.state.model`, appends a model-change entry, adjusts thinking level and emits `model_select`. `options.persist` additionally writes defaults. `cycleModel()` chooses among available/scoped models and records the change. **Neither inspected model mutation path enforces an idle/streaming guard.** This does not prove a running request changes transport mid-response; it proves the setter alone cannot guarantee serialized, correctly attributed turn transitions.

The RPC `set_model` handler finds a provider/model pair in the available snapshot and calls `session.setModel(model)` directly. Unknown pairs return a failed command response; RPC does not add an idle fence. `cycle_model` returns null when no alternative exists. A successful command therefore does not establish Splyce's egress/config transition guarantees.

**Proposed Splyce behavior:** serialize replacement against admission, then either wait for the existing turn to finish under its original contract or abort and await `waitForIdle()` before replacement. Preserve outcome/partial-output attribution; never splice two providers into one claimed turn, replay an uncertain effect, or reinterpret a saved local turn as authorization to upload its history. Bind future queued work to current policy, while old results remain labeled with their original revision. Recheck provider/endpoint changes discovered during auth refresh and virtual routing, not only picker selections.

## New, resume, fork and tree semantics

[Session docs](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/sessions.md) distinguish `/new`, `/resume`, `/tree`, `/fork` and `/clone`. CLI `--continue` selects the latest session for the working directory; `--resume` opens a picker; `--session` selects an existing session; `--no-session` is ephemeral. These operate on local conversation state, not a hosted Responses conversation identifier.

| Existing owner/API                                                        | Actual behavior and failure boundary                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SessionManager.create`, `open`, `continueRecent`, `inMemory`, `forkFrom` | Local persisted/in-memory session construction. Session entries form a JSONL tree through `id`/`parentId`; model/thinking changes participate in branch projection.                                                                                   |
| `SessionManager.branch(entryId)`                                          | Changes the active leaf in the same session; existing branches remain. Invalid entry fails. Subsequent appends form a branch.                                                                                                                         |
| `AgentSession.navigateTree(targetId, options)`                            | Same-file navigation, optionally summarizes the departed branch. Explicitly rejects streaming or concurrent compaction/navigation; missing summary model and invalid target are errors. Summary is a model operation with its own egress requirement. |
| `AgentSessionRuntime.newSession` / `switchSession`                        | Emits cancellable `session_before_switch`, then settles/aborts the outgoing session, emits shutdown, disposes old state, constructs and rebinds the replacement. Resume can change cwd/trust context. Cancellation preserves the existing session.    |
| `AgentSessionRuntime.fork(entryId, {position})`                           | Cancellable `session_before_fork`. Default `before` requires a user message and returns selected text; `at` includes the selected entry and implements clone-at-leaf behavior. Invalid entries or an unsaved persisted source can fail explicitly.    |

The exact owner matters: replacement methods are on [`AgentSessionRuntime`](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/agent-session-runtime.ts#L133-L349), not invented `AgentSession.newSession()` methods. Its teardown waits for `session.abort()` before disposing the outgoing runtime; this differs from the unguarded model setter. Replacement construction/rebind can still fail after teardown, so Splyce must reconcile a failed transition rather than advertise rollback or atomicity without a test.

[`SessionManager`](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/session-manager.ts#L1160-L1187) delays initial file creation until a user or assistant message exists; setup/model entries alone may remain in memory. Later entries append to JSONL. The source uses synchronous writes here, not an atomic transaction with Splyce's journal. `model_change` stores provider and model ID, not a complete endpoint/API/egress/asset contract. Branch projection restores conversation selection; it does not reconstruct consent for a newly configured cloud endpoint. Save Splyce's binding separately and revalidate on resume.

Forks/clones and compaction retain or copy source content; tree movement is not deletion. Inventory descendants and derived summaries for scoped retention/deletion. Pi's documented sharing commands upload transcripts externally; those are separate optional effects with explicit approval, never an implication of cloud generation consent.

## Headless interfaces and decisive tests

The [RPC source](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/modes/rpc/rpc-mode.ts) implements JSONL commands such as `new_session`, `set_model`, `cycle_model`, `get_available_models`, `switch_session`, `fork`, `clone` and `get_tree`. Command response success is distinct from cancellation: replacement may return `success: true` with `data.cancelled: true`. `get_tree` is inspection, not evidence of an implemented RPC tree-navigation command. RPC input handlers can overlap; command IDs correlate responses but do not serialize policy transitions.

Print/JSON mode binds lifecycle actions to the same runtime owner, emits session events in JSON mode and processes supplied prompts. Without a UI, the extension runner's default confirmation returns false and selection/input return undefined. RPC instead offers an extension-UI request/response channel. Headless approval therefore requires an explicit supported channel or denial; print mode cannot inherit an interactive prompt. Print text output maps terminal error/aborted/truncated assistant responses to failure, while event streams still need their own semantic interpretation. [Mode source](https://github.com/earendil-works/pi/tree/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/modes), [RPC command reference](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/rpc-commands.md).

Proposed tests must use the real loaded Pi entrypoint: local-only generation with forbidden cloud summarization; explicitly admitted cloud generation with unauthorized data withheld; Chat Completions/Responses/Messages/Gemini partial tools, terminal errors and cancellation; credential-helper discovery without execution; model change during stream/tool dispatch; concurrent RPC replacement; resume after endpoint/egress change; cancelled new/fork/switch; failure during teardown/rebind; branch/fork deletion descendants; print versus RPC approval. Contract fixtures do not establish actual vendor behavior; actual-provider opt-in tests and installed-platform results remain separately required.
