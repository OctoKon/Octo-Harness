# Pi packages for a barebones Splyce installation

**Reviewed 2026-10-25. Source-observed, unimplemented; installation, lifecycle and resource measurements n=0.** This audit reads official Pi at `d5b3de22d0e24a3e9c38a9410d3329b099717283`, not the moving main branch or a qualified npm release. [PKG-01–PKG-10](../evidence/pi-package-sources.json) record the sources. The current product direction is a barebones Pi-based installation: no RAG, LSP or other optional module is required. Users choose components during setup and may add, remove or toggle them later. Fetching selected components from a Git repository is provisioning, not permission to start their workers or send model data elsewhere.

## Existing mechanism to reuse

Pi packages contain extensions, skills, prompt templates and themes. A directory can use conventional resource folders or an explicit `package.json` `pi` manifest. This is a resource package mechanism, not a universal service supervisor or model installer. An optional RAG or LSP capability would need its own reviewed extension and runtime integration; merely installing its files does not qualify that capability.

The pinned [package documentation](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/packages.md) and [CLI reference](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/cli.md#package-commands) establish these real commands. Examples use placeholder packages and were not executed:

```sh
pi install git:github.com/example/pi-tools@v1
pi install npm:@example/pi-tools@1.0.0
pi install ./local-package
pi list
pi config
pi remove git:github.com/example/pi-tools@v1
pi update --extensions
```

`--local`/`-l` on install, remove or config selects project scope. `pi uninstall` aliases remove. `pi update <source>` updates one configured identity; `pi update --extensions` updates packages rather than the Pi host. `pi -e <source>` tries resources for one invocation without persisting a package entry, but can still provision dependencies; it is not a no-install preview. For a reproducible Splyce Git selection, replace the illustrative tag with a reviewed full commit ID and record the resolved commit.

## Resource selection is distinct from installation

An explicit package manifest selects resource roots; without it, Pi discovers `extensions/`, `skills/`, `prompts/` and `themes/`. A settings package object can narrow each type. Omitted properties load the package's allowed defaults; `[]` loads none of that type; exclusions and exact-path overrides are available. `pi config` controls discovered resources and built-in extensions. Filters cannot expose resources absent from the package's declaration. See [collection logic](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/package-manager.ts#L2245-L2293).

**Important limit:** a disabled resource is not an absent installation. `DefaultResourceLoader.reload()` calls package resolution before filtering `noExtensions`/`noSkills`. The package manager can install a missing configured npm/Git source before considering its resource filters. A package with every resource type filtered out can still require provisioning. Offline mode skips missing-source installation; the manager also exposes an `onMissing` decision, but the default loader calls `resolve()` without supplying it. See [loader order](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/resource-loader.ts#L540-L617) and [missing-source handling](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/package-manager.ts#L1298-L1368).

Therefore Splyce must distinguish available catalog entries from installed package declarations. Unselected components stay out of Pi's configured package set. Normal startup/reload must not fetch a missing installed component silently: report it unavailable and offer an explicit provisioning action. Reuse the existing resource-loader integration seam or record the smallest qualified Pi patch if necessary; do not invent a settings flag for this behavior. A failed required Splyce boundary cannot inherit Pi's warning-and-continue behavior.

Barebones also requires controlling discovery. Pi auto-discovers user/project resources and certain ancestor `.agents/skills` directories, and its built-in `mcp`, `llama.cpp`, `codemode` and `tool-search` extensions load by default. Empty `packages` alone is insufficient. Use the owned agent directory plus an explicit qualified resource selection, including project resources and built-ins. Pi's documented `--no-extensions`, `--no-skills`, `--no-prompt-templates` and `--no-themes` suppress discovered/configured resources while explicit resource arguments can still load; they are not trust boundaries or fetch suppression. [Settings](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/settings.md#resources), [discovery](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/package-manager.ts#L2444-L2525).

## Pins, dependencies and code trust

Exact npm versions are pinned; version ranges remain ranges. Git refs select checkout targets and explicit reconciliation can fetch them again. A mutable tag/branch is not an immutable commit guarantee. Ordinary startup accepts an existing Git checkout at its managed path without verifying its HEAD against the configured ref. A source string alone therefore cannot establish the bytes loaded. Splyce must record and validate actual resolved revision, dirty state and distributed artifact/dependency inventory before activation. No independent Splyce signature or content-attestation guarantee was observed in the inspected manager; npm/Git transport and lockfiles do not replace a qualification receipt. [Resolution](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/package-manager.ts#L1340-L1366), [updates](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/package-manager.ts#L1138-L1156).

Git installation clones the repository, checks out its requested ref and installs package dependencies when `package.json` exists. npm uses its managed installation root. The observed installer arguments do not universally suppress lifecycle scripts; these paths can execute package-controlled installation work before extension loading. Resource filters do not prevent dependency installation. Reviewed provisioning therefore needs a separate scoped network/filesystem/process grant and recorded dependency/build inputs; a package request cannot silently authorize executable setup. [Installer arguments and Git install](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/package-manager.ts#L1848-L1953).

Pi documents host-supplied packages as peer dependencies and suppresses automatic peer installation for supported managed installers. Other runtime dependencies belong in `dependencies`; local packages must prepare their own tree. Package roots do not imply shared dependency instances. Git installs use production-oriented arguments for recognized npm/pnpm/Bun commands, while an unrecognized wrapper falls back to plain `install`. A fixed top-level commit does not freeze transitive versions or install behavior. Per-component installation from one monorepository is not sparse checkout: installing a package can fetch the whole repository and its declared dependency set. Keep optional components in independently installable packages, or disclose the actual shared download/dependency burden rather than claiming byte-level modularity.

Git reconciliation can reset/clean its managed checkout and reinstall dependencies; Git removal deletes that checkout. Keep user data, edited source and model weights outside disposable package roots. Local-source removal is deliberately different and does not delete the original. [Reconciliation and removal](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/package-manager.ts#L2006-L2068).

## Lifecycle and durable ownership remain Splyce work

Pi already supplies settings persistence and reload lifecycle; reuse them. Installation precedes persisting its source, while removal precedes dropping that source. These are separate operations, not one durable transaction spanning filesystem, settings and active session. Settings writes are queued and locked; `flush()` waits for the queue, while `drainErrors()` exposes recorded failures. Awaiting a queue alone does not certify a successful configuration commit. [Package methods](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/package-manager.ts#L1052-L1104), [settings persistence](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/settings-manager.ts#L576-L677).

`AgentSession.reload()` emits `session_shutdown`, invalidates the previous runner, reloads settings/resources and rebuilds runtime bindings before the next `session_start`. It does not establish that arbitrary extension-owned processes, files, timers or external services have been cleaned. Removing a package from disk is not proof that already loaded code stopped. [Reload source](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/agent-session.ts#L3720-L3758) and [extension lifecycle](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/extensions.md) provide the seams to qualify.

The minimum missing Splyce contract is selection/install/enable as separate states, exact source/version/scope ownership, admission fencing before disable/remove, cancel/drain and cleanup receipts, shared dependency references, explicit asset deletion and restart reconciliation. A failed settings write, interrupted install or failed teardown remains visibly incomplete. External user-managed services and local source files survive removal. Installing an optional component never enables dependent capabilities or downloads models implicitly. Reuse Pi's resource controls; add only these missing guarantees, not a second package manager or autonomous loop. [Capability lifecycle](../design/capability-map.md), [user models](../design/user-controlled-models.md), [implementation contracts](../design/implementation-contracts.md).

Pi also documents `enableInstallTelemetry: true` by default and separate update checks. This differs from Splyce's no-unsolicited-telemetry requirement. Explicitly qualify disabled telemetry and startup networking across fresh install, update and reload; a bare package list proves neither. `--offline`/`PI_OFFLINE` are documented host controls, not a sandbox on arbitrary extensions or package scripts. [Telemetry settings](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/settings.md#updates-telemetry-and-warnings), [environment controls](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/docs/environment-variables.md).

## Required proof before advertising modular installation

These are proposed tests, not available commands or executed results:

| Fixture                       | Required observation through Pi's loaded user path                                                                                                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Empty selection               | Fresh barebones install/start/reload has no RAG/LSP/optional package assets, workers or downloads; inspect built-ins and ambient/project discovery as well as the package list.                                         |
| Explicit Git component        | Setup selection and later add resolve the approved full commit, enumerate actual dependency/download bytes and persist only the selected scope. No model download or unrelated component activation.                    |
| Disable versus uninstall      | Toggle fences calls and releases owned residency while retaining installed files; remove cleans only owned package artifacts after reference checks. Other roles, external services and local original sources survive. |
| Missing or changed bytes      | Delete a configured package, change a Git ref/working tree, or start offline: no unapproved repair/download or activation; explicit unavailable/mismatch state.                                                         |
| Install/settings interruption | Interrupt provisioning and fail settings persistence; restart reconciles one intended state, checks recorded write errors and never falsely claims installed/enabled success.                                           |
| In-flight removal             | Disable/remove during a call, then reload: no late dispatch/publication, orphan worker or replayed uncertain effect; cleanup failure remains visible.                                                                   |
| Shared repository             | Select two resource groups from one repository: observe one effective package version and the full fetched dependency burden; removing one does not silently break the other.                                           |
