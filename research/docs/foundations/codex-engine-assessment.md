# Codex engine versus Pi: reuse and transition assessment

**Reviewed 2026-10-26; source/document review only, engine comparison and Windows runtime qualification n=0.** The user requested Codex as the frontend reference and asked whether its engine is closed source. The answer concerns distinct layers, not a performance winner. [CFND-01–09](../evidence/codex-foundation-sources.json) bind this pass to public sources and Codex revision `970111f6cb62cc02fe36a82ea7d71b37a2889c97`.

## What can actually be reused

The open Codex CLI/engine is Rust and Apache-2.0 licensed [CFND-01, CFND-04]. Its app-server is a documented custom-client seam [CFND-03]. The desktop interface, hosted inference models, account entitlements and cloud services are separate layers; an OSS engine license does not transfer those rights. Retain upstream LICENSE/NOTICE and qualify all actually shipped dependencies [CFND-01–02]. Splyce's own AGPL-3.0-only project license remains unchanged; third-party components retain their original terms. This research grants no new distribution entitlement.

Use Codex's desktop workflow and complementary Claude interaction patterns as **design references**, with original Splyce assets/components. That frontend direction neither requires the Codex engine nor licenses a pixel/source copy. See the [frontend research](../frontend/README.md).

## Integration routes are separate experiments

- **Private stdio app-server child:** the documented rich-client route, with a process/framing/lifetime boundary and the support-warning ambiguity above. Qualify handshake, cursors, backpressure, cancellation, quit/restart and the complete shipped closure [CFND-03].
- **Pinned Rust-core embedding:** the inspected source exports configuration and `ThreadManager`; public symbols establish a possible investigation path, not a stable consumer SDK. Audit workspace/runtime coupling, native admission points and upgrade maintenance before selecting it. Fewer processes do not prove lower installed cost or resource use [CFND-08].
- **SDK automation:** the official SDK guide distinguishes task automation from app-server rich clients. Its TypeScript/Python runtime choices require a concrete benefit and full closure accounting; do not add either runtime to a Rust experiment by default [CFND-09].

## Current disposition and minimal next decision

**Codex is a viable OSS foundation candidate; it is not excluded as closed source.** Pi remains the canonical engine in current executable task contracts until an explicit foundation decision retargets them. No Codex runtime has been installed or integrated in this research pass. Frontend contract/component work may proceed against frozen typed fixtures independently; engine-specific integration cannot assume both foundations simultaneously.

**Stage A — source/design and experiment disposition:** TD-01/Itachi owns a foundation record reviewed by both leads before engine-specific contracts freeze. It pins sources/licenses, compares the three routes above, names the native boundaries and affected contracts, and specifies an owner, synthetic fixtures, resource budgets, stop conditions and allowed experiment paths. Planned candidate paths are `tests/foundations/codex/` and `research/qualifications/foundations/`, on a dedicated username-prefixed branch; they are future paths, not implemented runners. No real user history/configuration is imported. A bounded prototype may be authorized without completing later Pi-specific tasks. A source-backed engine-direction decision must explicitly retarget every affected contract; it cannot inherit Pi qualification. This research-only PR starts no prototype and changes no engine decision.

**Stage B — runtime/support admission:** the same record must contain the following actual evidence before shipping the selected foundation or making support, production or superiority claims. Stage A permission is not Stage B success:

1. Immutable Codex/Pi pins, actual build targets/dependencies/licenses and Windows cells; no moving main-branch build.
2. Exact native symbols for generation/tool/approval/session/persistence/output boundaries and the minimal owned-fork patch map. App-server JSON shapes alone are insufficient.
3. Matched deterministic fault fixtures for deny/revoke, interrupted effects, crash/reopen, replay/cursor, snapshot verification and base deletion, including all selected entrypoints.
4. Actual opt-in local/cloud provider cells needed for the first release, including no-account local startup and explicit native-protocol or selected-local-translator limitations. Unknown capabilities remain unavailable.
5. Identical Windows GUI workflows, model/task/grants and full resource accounting. A source advantage can justify a prototype, while a production or superiority claim requires paired results with failures and n.
6. A complete affected-file map: root AGENTS/master/README, stack/runtime packaging, source contracts, records/session storage, module format, provider fixtures, implementation skill, every affected TD path/dependency, CI/release/SBOM and upgrade/rollback. Existing TD IDs remain stable where their responsibility survives; changed semantic ownership needs a new reviewed revision.

A switch must choose **one native engine**. Do not launch Pi beneath Codex to recover provider coverage or combine their independent session/effect authorities. Reuse donor code only with license/provenance and a native integration contract. A decision that requires more translator/runtime/authority complexity than it removes should be rejected or narrowed. Retain the Pi baseline and record counterevidence rather than replacing it because Rust or a polished desktop looks preferable.
