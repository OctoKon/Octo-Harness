# Desktop GUI stack decision

**Locked architecture stack, 2026-10-25; Windows-only V1 and frontend-tooling reconciliation 2026-10-26; implementation, installation and performance measurements n=0.** Splyce is a proper desktop GUI application with a Splyce-owned Pi-derived headless engine. V1 is Windows desktop GUI only, with no CLI/TUI product surface. Pi's existing loop is retained internally; upstream headless interfaces are implementation mechanisms, not a second user interface. Linux and macOS are future research only and do not gate V1. This supersedes earlier terminal-first and extension-only client wording. [Master plan](../../../MASTER-PLAN.md) owns product acceptance; [DESK-01–DESK-23](../evidence/desktop-stack-sources.json) record public sources accessed for this decision. Locked choices let the frontend team start against frozen fixtures; they do not imply runtime qualification or freeze untested patch versions.

Use **npm workspaces** for the desktop and Pi-derived packages, **Node 24 LTS for development** and the qualified packaged engine runtime. Node 24 entered Maintenance LTS on 2026-10-20 with end of life on 2028-04-30, and Node 26 becomes Active LTS on 2026-10-28 ([Node.js release schedule](https://github.com/nodejs/Release#release-schedule)). The MXC Node SDK, the preferred Windows executor candidate, needs at least Node 24.21.0 or 26.8.0 on Windows, which sets the patch floor. Node 24 stays the locked selection until TD-11 records an explicit 24-versus-26 decision with its end-of-life date and runtime-upgrade drill; the support manifest carries `nodeMajor` and that date, and a packaged runtime past its maintenance end blocks release. Frontend state uses **Svelte 5 runes**, with built-in stores/context for shared state; no extra global-state library is required. Quality tools are **Prettier + `prettier-plugin-svelte`, ESLint + `eslint-plugin-svelte`, `svelte-check` and TypeScript strict checks**, followed by the actual Vite/Tauri build and packaged Windows GUI E2E. The [official Svelte ESLint plugin](https://sveltejs.github.io/eslint-plugin-svelte/) documents Svelte-aware linting; [Svelte check](https://svelte.dev/docs/cli/sv-check) covers Svelte/CSS/JS/TS diagnostics. Static checks do not replace E2E or prove runtime message validation. [Tauri channels](https://v2.tauri.app/develop/calling-frontend/) carry engine streams; typed frontend APIs still require privileged runtime validation.

The framework families above are decided. Reopening them requires a recorded failing product gate or paired measured benefit, not another preference poll. Exact Rust/Tauri/Svelte/TypeScript/Vite/Node patches, platform drivers, lockfiles and loaded-byte identities remain **TD-11's validated-build freeze**; no moving `latest` range enters a released build. Node's [official release table](https://nodejs.org/en/about/previous-releases) lists Node 24 as LTS. [Node 24.22.0](https://nodejs.org/en/blog/release/v24.22.0), dated 2026-10-14, is a concrete candidate inspected here, not an installed or asserted latest patch. Pi's Node >=22.19.0 declaration admits 24 by version range; that alone does not prove SDK, plugin or native dependency compatibility.

The official [Tauri templates](https://v2.tauri.app/start/create-project/) explicitly include Svelte, Solid and React. Svelte with Vite can build the required local assets directly; a full-stack SSR framework adds no required role to this desktop contract. [Vite 8's announcement](https://vite.dev/blog/announcing-vite8), [support policy](https://v8.vite.dev/releases) and [v8.3.5 release](https://github.com/vitejs/vite/releases/tag/v8.3.5) establish the chosen build-tool family and observed patch, not a Splyce speed or install-size result. Development/build dependencies are excluded from the shipping runtime unless the actual dependency audit proves they are required.

This is a contract-fit and maintenance decision, not a universal framework ranking or measured frontend benchmark. Each route could pass; real Tauri WebView accessibility, composition/IME, long transcripts and event batching remain acceptance gates for the selected route. No framework guarantees accessible widgets merely by compiling them.

The user-selected optional editor is **[Monaco](https://github.com/microsoft/monaco-editor)** for rich coding ergonomics. It is separately installed and activated; the base ships **zero Monaco/editor/language-worker payload** and retains simple text/diff views. Package ESM editor assets and selected workers locally, without CDN/network loading. Qualify URI/protocol/CSP behavior, worker disposal, keyboard escape/focus, IME, screen-reader use, large files, safe writes and stale-revision rejection through the packaged Windows application. Monaco is not a VS Code extension host; LSP integration remains a separate selected module. Do not adopt the vendor's worker-overhead reassurance as a Splyce measurement.

**CodeMirror 6 remains a comparator, not the selected editor or a co-bundled fallback.** Its [official development repository](https://github.com/codemirror/dev) directs consumers to separate npm packages and records its move to `code.haverbeke.berlin`; the [view repository](https://github.com/codemirror/view) identifies the DOM view component. The legacy `codemirror/codemirror` URL redirects to version 5. The website guide and new forge returned HTTP 403 during this sweep; current package revisions and deeper API compatibility were not inspected. No claim that either editor is universally smaller or more accessible follows from this choice.

## Default and bounded alternatives

Choose **Tauri 2, Svelte 5 and TypeScript**, compiled to local static assets, with a minimal Rust desktop shell and an owned **Node.js child running the Splyce Pi-derived core through its qualified SDK/headless interface**. No SSR server, browser-hosted service, second model loop, Rust port of Pi, or Bun compatibility assumption is needed. This is the default to qualify, not a measured claim that it is the smallest possible application. Ship no alternative GUI framework alongside it.

| Route                                                      | Useful mechanism                                                                                  | Complete cost and qualification tradeoff                                                                                                                                                                  | Disposition                                                                                                                                               |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tauri 2 + Svelte 5/TypeScript + Rust shell + Node/Pi child | Platform WebView, explicit frontend capabilities, compiled web UI; preserves Pi's TypeScript APIs | Rust host, WebView processes and dependencies, Node/Pi and tools all count. Engine variation and child lifecycle need real OS tests.                                                                      | Default: avoid bundling a second browser engine; retain a familiar accessible DOM UI.                                                                     |
| Electron + web UI + Pi in an owned utility process         | Bundled Chromium/Node, consistent renderer and direct Node ecosystem reuse                        | Bundled browser distribution and multiprocess footprint; qualify Electron's Node version against Pi and native dependencies. Can avoid a separate Node distribution, so compare complete packages fairly. | Reconsider only if the default fails required rendering/accessibility/integration gates and Electron passes the same gates with acceptable measured cost. |
| Native Rust + Slint + Node/Pi child                        | Declarative native UI with Rust integration; no web renderer requirement                          | Still needs Pi's Node child; new widget, rich transcript, accessibility and packaging work. Slint license selection adds obligations.                                                                     | Bounded native challenger if full-process measurement justifies its engineering cost.                                                                     |
| Native Rust + egui/eframe + Node/Pi child                  | Immediate-mode Rust UI; optional AccessKit integration                                            | Still needs Node; transcript selection, IME, focus, screen-reader and desktop conventions require qualification. No inference that native means lower idle CPU or RAM.                                    | Challenger only after the same real user-flow and OS gates.                                                                                               |

Tauri's [WebView documentation](https://v2.tauri.app/reference/webview-versions/) names WebView2 on Windows, WKWebView on macOS and WebKitGTK on Linux. Platform rendering dependencies are not free merely because the app does not bundle Chromium. Electron's [process model](https://www.electronjs.org/docs/latest/tutorial/process-model) separates privileged Node main/utility processes from renderers; [distribution prerequisites](https://www.electronjs.org/docs/latest/tutorial/tutorial-prerequisites) establish that Chromium and Node are bundled. These are architectural observations, not resource measurements.

GPUI is not a fifth framework to build in parallel. Reopen that candidate only for a concrete unsatisfied gate with a frozen source/license/platform review. This bounded comparison does not assert that an untested candidate lacks a feature.

## One engine and one privileged boundary

The locked path is local Svelte UI → narrow Rust commands/channels → private stdio Node bridge → Splyce's Pi-derived SDK/core. Pi's existing turn, streaming, tool, provider, compaction and branch machinery is the starting implementation. Splyce may modify actual model-runtime, tool-dispatch, session, provider and lifecycle contracts to integrate policy, operational receipts and desktop approvals coherently; a failed extension hook is not a prerequisite for a justified core change. Keep one execution path and preserve upstream notices, ancestry and regression evidence. The shell owns window/native-dialog integration and child lifetime, not a second conversation engine or separate store of authoritative session state.

The public upstream pin above is a reference audit baseline, not the future Splyce fork revision. Freeze upstream ancestry, fork commit, patches, lockfiles and built-byte identities before qualifying a release. Optional capabilities use native core interfaces and explicitly installed plugins; placing an interface in core does not install or enable its optional implementation, service or model by default.

Prefer the SDK/headless bridge so core policy readiness, explicit resource loading, selected extension binding and approval transport can be qualified together. Reuse or evolve Pi's existing RPC framing/events where suitable; a stock `pi --mode rpc` process alone does not establish the fused core contract. Do not render a terminal emulator and label it a GUI. Do not treat print/JSON no-op UI prompts as approval. The [pinned upstream SDK](https://raw.githubusercontent.com/earendil-works/pi/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/coding-agent/src/core/sdk.ts) exposes explicit model/resource/session inputs and a fallback warning: Splyce must block until the user selects a valid provider/model and must reject silent restoration fallback. Constructing an upstream session alone is not proof that policy is ready. New fork APIs remain unimplemented proposals until source-pinned and tested.

**Required boundary:** render workspace/model/plugin text as untrusted data. Serve local packaged assets; deny remote navigation and avoid granting remote pages IPC. Tauri [capabilities](https://v2.tauri.app/security/capabilities/) constrain frontend access, not malicious Rust or trusted Pi extension code. Restrict each window to named commands; validate message shape, operation, request ID, effective profile revision and workspace scope in privileged code. Recheck grants at actual Pi effect dispatch. Never expose arbitrary shell/process/filesystem APIs or a raw unvalidated Pi command passthrough to the renderer. Keep credentials outside renderer state, exported receipts and logs. Apply CSP and safe transcript rendering; no raw HTML execution from model output.

**Required lifecycle:** package a pinned Node executable and qualified Pi distribution for each advertised Windows version/architecture, rather than depending on ambient Node or downloading it on first launch. Tauri's [sidecar mechanism](https://v2.tauri.app/develop/sidecar/) supports target-specific binaries; its [Node example](https://v2.tauri.app/learn/sidecar-nodejs/) is guidance, not proof that its packaging recipe supports Pi's dynamic extensions, imports and native dependencies. Initially prefer explicit Node plus JS/resources over an unqualified single-file bundler. Check executable/resource hashes, runtime version, controlled cwd/environment and protocol handshake before use. Keep stdout protocol-only and scrub stderr diagnostics. Bound individual messages and apply backpressure without imposing an arbitrary agent/context cap.

Own the child and its descendants: cancel/drain active work, persist final or uncertain receipts, close channels, terminate/reap when needed, and record incomplete cleanup. Test close-window versus quit, crash, reload, logout/shutdown, parent death, child death, blocked pipes, lost response and restart. Platform process-tree mechanisms must be qualified individually; a successful direct-child kill does not establish descendant cleanup or remote cancellation. No background daemon, autostart or hidden process restart by default. When the engine exits, Rust emits `engine_exited` with its code; the GUI shows **Engine stopped** with an explicit **Restart** action, Rust respawns only on that command after the identity/handshake check, and TD-25 reconciliation completes before any task is admitted. Reopening the UI must reconcile effects before retrying and retain a readable failure screen if Pi cannot start.

## Barebones GUI and first flows

The minimum install contains the desktop shell/UI, required runtimes and Pi-derived core with native policy/receipt/verification contracts. Basic file/search/edit/process tools reuse Pi. No default model/provider selection, weights, RAG, cross-session memory, LSP, skill pack, external server, driver, delegation worker or optimizer is installed or activated. Core receipts and Pi sessions are not optional RAG. Follow [modular installation](../design/modular-installation.md), [provider/profile/session contracts](../design/providers-profiles-and-sessions.md) and [custom plugin contracts](../design/plugin-authoring.md).

Use one main window, a workspace/session rail, task transcript and an inspectable details pane. Compact layouts collapse panes without removing controls. This screen map specifies workflows, not implemented screens or an additional dashboard dependency.

| Surface                         | Minimum flow and visible state                                                                                                                                     | Decisive negative/recovery case                                                                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Setup/modules                   | Base-only/skip is prominent; optional selection shows pinned sources, full dependency closure and download/activation separately.                                  | Skip yields no optional fetch/load/process; failure preserves previous usable install and gives a retry/remove route.                               |
| Workspaces/tasks                | Open local workspace; create task/acceptance; inspect diff, run state and exact final verification evidence.                                                       | Invalid/moved workspace, stale base and failed verifier cannot appear complete; cancel reports actual cleanup.                                      |
| Providers/profiles/model picker | Add explicit local/cloud connection; show endpoint/locality, credential reference and per-operation selection. Picker accessible before a turn and on live switch. | Empty/unreachable/incompatible selection blocks with actionable explanation; change fences queued work and records the immutable run binding.       |
| Sessions/branches/forks         | Browse, resume, navigate and fork Pi history with explicit source session/entry; show ownership/conflict.                                                          | Concurrent writer, interrupted load or missing model cannot silently substitute a branch/profile or lose evidence.                                  |
| Approvals                       | Present exact action, target, scope, provider/egress, current grants and allow/deny before dispatch; keyboard focus returns to origin.                             | Closed/stale/disconnected prompt denies or remains explicitly blocked; never infers consent or grants broader scope.                                |
| Plugins                         | Install explicit local folder/custom Git revision; inspect compatibility, trust, grants and dependencies; enable/disable/update/remove separately.                 | Rejected revision/load failure preserves working state; trusted in-process code is labelled honestly; removal offers retained-data export/deletion. |
| Evidence/errors/settings        | Inspect receipts/artifacts, uncertainty, source revision and exact check results; accessible diagnostics, offline state, export and theme settings.                | No secrets/stack leaks; uncertain outcome remains uncertain after restart; copy/export reports failures and does not erase source evidence.         |

V1 has no CLI/TUI support obligation. No TUI-only extension UI is silently accepted as desktop support. Plugins declare client compatibility; Pi tools/providers can be reused without promising arbitrary upstream terminal widgets appear in the GUI. Desktop contributions use a reviewed typed surface rather than unrestricted script injection into a privileged window.

## Packaging, updates and measured gates

The [Windows installer guide](https://v2.tauri.app/distribute/windows-installer/) distinguishes WebView2 bootstrap, offline installer and fixed-runtime modes. A small bootstrap download is not offline installation. Offer a clearly labelled ordinary installer and, only when qualified, an offline dependency-complete package; show runtime prerequisites before installation. Future Linux research must qualify its WebKitGTK/GTK closure; future macOS research must qualify OS WebKit and signed resources. Neither platform is advertised or required for V1.

Updates are explicit user actions; no unsolicited network check, telemetry or module install. Initially a verified manual installer is sufficient. If the optional updater is selected, Tauri [requires signed update artifacts](https://v2.tauri.app/plugin/updater/); additionally test provenance, platform/architecture matching, interrupted transfer, failed activation, migration and recovery. Update the app, Pi and Node as a compatible frozen set; do not replace a live engine mid-action. An offline profile continues to open local state and receipts; only operations needing unavailable endpoints fail clearly.

Freeze equal workloads and quality/authority gates before comparing the four routes: base-only first launch, idle with no task, one streamed task, long transcript, cancellation/crash recovery and selected-module launch/removal. Record compressed installer and actual installed/dependency disk bytes, download bytes, cold/warm time to usable UI and first engine readiness, total process-tree idle/peak memory and CPU, GPU use, background processes after quit, and separately selected model/service costs. Disclose existing versus newly installed WebView/Node dependencies and shared-memory accounting; collect repeated paired trials on the same hardware/OS. Publish failures and sample counts. No route wins by a hello-world executable size or a borrowed vendor benchmark. Resource budgets must be declared before qualification; none are invented here.

Tauri's current [WebDriver guide](https://v2.tauri.app/develop/tests/webdriver/) documents `@wdio/tauri-service` with an embedded test WebDriver on Windows/Linux/macOS. Direct `tauri-driver` remains Windows/Linux only. V1 qualifies the Windows embedded route with the real app/bridge and no IPC mocks; keep test-only server plugins out of shipping builds. Browser-only mocked UI checks cannot establish installed OS behavior. [Svelte accessibility warnings](https://svelte.dev/docs/svelte/compiler-warnings) catch some markup errors, not screen-reader usability; [egui](https://github.com/emilk/egui) likewise documents optional AccessKit, not universal accessibility proof.
