# Efficiency and recursive improvement: evidence chains

Reviewed **2026-10-25**. Public-source research and proposed experiments only: Splyce runtime, quality, latency, footprint and savings results are **n=0**. The [PF source ledger](../evidence/efficiency-sources.json) records the selected primary evidence. This extends [recursive harnesses](../foundations/recursive-harnesses.md), [evidence efficiency](evidence-freshness-and-token-efficiency.md) and the [memory mechanism review](memory-mechanism-review.md); it does not replace their qualification gates.

The [master plan](../../../MASTER-PLAN.md) selects Pi with local execution and state. Generation, extraction, embeddings, reranking, and improvement trials each use a recorded local or explicitly authorized cloud profile; no provider switch or fallback is silent. Hosted memory and executors remain comparison evidence, not deployment dependencies. No engine, API profile, hardware profile, or optimization below is qualified for Splyce.

## What agents still lack

An agent can generate quickly while completing slowly: it may inspect the wrong evidence, repeat a failed search, serialize independent reads, start unnecessary models, retry an uncertain effect or spend several turns repairing a plausible edit. A token reduction can hide the one exception needed for correctness. An impressive warm-cache result can hide model loading and indexing. These are engineering hypotheses to test, not measured diagnoses of every agent.

The missing contract is successful work per total resource budget, with evidence of correctness, recovery and scope preservation. Optimize the longest dependent path from task admission to durable verified result. That path includes queueing, evidence discovery, prefill, decode, tools, verification and recovery; parallel branches contribute their critical path rather than a fictitious sum of overlapping durations. Report total CPU/GPU work separately: a shorter wall time can consume more resources.

Start with one loaded Pi entrypoint, a qualified local SQLite operational store, lexical original-source recall and selected evidence expansion. Preserve Pi's loop and session ownership. SQLite driver selection and Pi/store reconciliation remain governed by the [implementation contracts](../design/implementation-contracts.md). Graph/vector retrieval, rerankers, speculative models and recursive improvement are optional challengers. Their extra installation, construction, idle and failure costs must earn their place against this baseline.

## 1. Harness²: improvement can transfer knowledge while multiplying attempts

**Evidence chain:** [paper v1, PF-01](https://arxiv.org/html/2610.14224v1) → [pinned recursion implementation, PF-02](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/harness2/core/recursion.py). The paper treats harness surfaces as editable while model weights stay fixed. An improvement library can preserve reusable lessons instead of rediscovering them on every task. This is a promising way to improve prompts, retrieval guidance, skills and tool use without training a new model.

**Limit found by following the mechanism:** the selected recursion file's header describes **4 × k rollouts and 3 × k improvement stages**, including shared base executions; these are counts parameterized by the recursion budget, not token limits. `STAGE_ATTEMPTS = 2` bounds the documented proposal retry. Stage records track USD, attempts, a cache-status flag and errors. Improving the harness is additional work before its successor solves anything. A candidate can win on tuning examples or a fallible judge and regress elsewhere; short answers and disabled checks can appear efficient under an incomplete objective.

**Mitigation and counterevidence:** the explicit stage accounting is useful counterevidence to treating improvement as free. The paper distinguishes sequential and parallel exploration; neither implies a desktop always needs both. Reuse accepted lessons, deduplicate already tested candidates and stop at the registered improvement budget. But amortization requires future reuse: a rarely repeated task may never repay optimization. Larger exploration is justified only by measured downstream value, not by the presence of a recursion feature.

**Splyce contract:** evaluate candidates offline in isolated local workspaces, outside Pi's trusted execution path. Freeze parent revision, fixture, model/runtime, grants, acceptance criteria and held-out tasks. A candidate cannot approve itself, change the judge's criteria, weaken policy or make external effects replayable. Store diff, parent, trial IDs, failed/interrupted attempts, resources, rollback target and independent adoption decision. Include local evaluator and improvement-model resources; upstream USD accounting is not a measurement of local electricity or ownership cost.

**Decisive test PF-A:** compare unchanged Pi/Splyce with one fixed candidate on matched held-out tasks after tuning closes. Charge generation, evaluation, unsuccessful proposals and all improvement stages to the candidate. Report the number of future tasks needed to recover this cost for declared reuse counts, including a one-use case; if the measured per-task saving is absent, no break-even claim exists. A permission-weakening candidate must fail regardless of judge score. No improvement adopts itself into the running host.

## 2. DeepSeek Harness: lifecycle ownership can prevent duplicate work

**Evidence chain:** [pinned architecture, PF-03](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/docs/architecture.md) separates durable session facts from live events, freezes model history before a streaming request, describes tool pre/execute/post phases and assigns disposal ownership. This makes a useful distinction: UI activity and in-flight deltas need not cause repeated reconstruction of the authoritative conversation.

**Limit and counterevidence:** composition and reversible registrations provide useful seams; they are not proof of crash durability, safe teardown under every race, or lower overhead. Freezing a request snapshot supports consistency but does not authorize stale queued tools after permission withdrawal. A typed event log does not establish that every event has reached durable storage. The project is developer preview; replacing Pi with another extensible loop would add lifecycle/version risk without satisfying a missing requirement.

**Mitigation and Splyce contract:** borrow snapshot and ownership semantics at Pi's existing boundary. Construct model input once from a bound source generation; reconcile new events on the next turn. Incrementally process committed source IDs instead of re-extracting complete histories. Every optional worker has an owner, cancellation path, durable cursor where needed and observable cleanup result. Share an already loaded local generation service for extraction only when its role-quality and scheduling contracts pass; otherwise extraction remains explicitly unavailable or uses a separately qualified local worker. Live events never replace committed operational receipts.

**Decisive test PF-B:** through the loaded Pi entrypoint, interrupt streaming, cancel a tool, revoke a queued grant and stop/restart an optional worker. Count model dispatches, extraction tuples and surviving processes; prove no duplicate committed observation, no falsely completed action and no dispatch under withdrawn authority. Measure teardown and next-task startup. A component plugin test cannot substitute for this user path.

## 3. Prefix and hierarchical caches: reuse computation, preserve eligibility

**Evidence chain:** [vLLM automatic prefix caching, PF-04](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/) explicitly reuses prefill computation, not decoding → [SGLang HiCache, PF-05](https://www.sglang.io/blog/hicache) describes a memory hierarchy whose restore must be cheaper than recomputation → [unified radix cache, PF-06](https://www.sglang.io/blog/unified-radix-cache) distinguishes FULL, sliding-window and Mamba state boundaries. These are different mechanisms, not interchangeable cache guarantees.

**Strength:** stable policy/tool prefixes and unchanged source blocks can avoid repeat prefill. A CPU or storage tier may preserve useful state that exceeds accelerator memory. Keeping stable prefixes ahead of changing context is a low-complexity candidate; it must not put stale authority into a supposedly immutable prefix.

**Limit and counterevidence:** a decode-heavy edit may see little benefit from prefill savings. Cold or low-reuse tasks can pay cache lookup/transfer overhead without a hit. Cache occupancy can evict more valuable requests, and disk/CPU transfers compete with indexing and model weights. HiCache's published benchmark is evidence of possibility in its publisher's configuration, not of this laptop's transfer economics. Hybrid state boundaries directly contradict a universal claim that every cached byte sequence can be sliced or restored like full-attention KV.

**Mitigation and Splyce contract:** qualify the selected engine/model pair, tokenizer/template, runtime and cache policy. Bind reuse to the engine's real validity rules and record hits, restored bytes and misses where observable. Never invent an engine API for scope-aware invalidation. Model KV/prefix state derived from retained material belongs in the retention inventory alongside retrieval caches. Deletion, permission change and model/template revision invalidate the appropriate reusable state; if the engine cannot enforce that scope, isolate the owned service or clear/restart it before a successful purge claim. Re-authorize evidence before hydration and dispatch even when computation is cached. A warm cache is not authority to recover deleted content.

**Decisive test PF-C:** run cold, warm repeated-prefix, changed-prefix, long-prefill and decode-heavy tasks with caching disabled/enabled on the same model contract. Compare TTFT, full completion, p95/p99, CPU/VRAM/RSS and cache traffic. Add two scopes, permission withdrawal, deletion and model revision change; verify the actual cache/service lifecycle prevents reuse outside the eligible scope. Include restart and failed purge. Retain caching only where full-task gains survive these costs and correctness gates.

## 4. Speculative decoding: exact sampling has workload conditions

**Evidence chain:** [Fast Inference from Transformers via Speculative Decoding, PF-07](https://arxiv.org/abs/2211.17192) proposes draft generation with target verification and an exact-distribution argument under its algorithm's assumptions. This is stronger than an arbitrary heuristic that skips verification. It is not a promise of identical seeded outputs across implementations or a guarantee that an arbitrary smaller model meets the target's quality.

**Limit and counterevidence:** accepted drafts can reduce target decoding steps; rejected drafts still consumed computation. Draft weights, loading and KV state increase footprint. Acceptance, target/draft speed ratio, output constraints and memory contention determine benefit. The paper's speed results establish its tested conditions, not every local engine, grammar or coding workload. A busy device can lose throughput despite reducing one request's serial target steps.

**Mitigation and Splyce contract:** admit speculation only as a qualified runtime option, with exact model/tokenizer compatibility and supported decoding constraints declared. Start the draft model on demand; include its cold load, idle retention and cancellation cost. Keep the same target model and preregistered task-quality floor. Smaller or quantized target models are separate quality experiments; a speed gain cannot silently lower that floor. Do not describe approximate draft-only shortcuts as the paper's exact algorithm.

**Decisive test PF-D:** alternate speculation off/on with the same target, prompts, output constraints, hardware and task budget. Measure accepted/rejected draft work where exposed, end-to-end latency, peak memory, total tokens/work and verifier outcomes on short/long outputs and both low/high acceptance workloads. Validate constrained tool output and cancellation. Treat missing runtime statistics as unknown; retain the ordinary target path when there is no supported, measured improvement.

## 5. Scheduling and early verification: optimize dependencies before adding agents

Independent file reads or local lookups can overlap; a verifier depends on the completed edit and cannot be moved earlier by calling it parallel. Overlapping generation with extraction may contend for the same accelerator and increase the user's tail latency. A delegated model introduces prompt construction, queueing, model residency, coordination and integration work. Count those costs rather than using worker count as a progress metric. This scheduling judgment is a proposed design, not a measured upstream comparison.

Use changed source identities to avoid duplicate indexing; preserve the [incremental/full-rebuild equivalence gate](evidence-freshness-and-token-efficiency.md#proposed-experiments). Reuse a valid observation by its idempotency tuple, not merely by similar text. Cache pure results only with source, tool and policy validity; never cache an uncertain effect as a successful retry. Run the cheapest relevant deterministic check after a change and expand verification when its result requires it. Early rejection should prevent repeated expensive model repair, while final verification still binds the final revision.

**Evidence and measurement limit:** [Node performance hooks, PF-08](https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html) can measure host timings and event-loop delay. They cannot establish model quality, accelerator energy or a completed task by themselves. An idle event loop may simply be waiting for slow inference. Instrument host spans and local runtime spans separately, then join them by run/action IDs without summing overlapping work.

**Decisive test PF-E:** compare serial and dependency-safe overlapped reads, then single-agent and one justified bounded worker, on matched tasks. Include a constrained device, cancellation, worker outage and uncertain tool outcome. Measure critical path, aggregate work, p95/p99 and verified completion. Reject delegation when saved task time does not repay coordination and lifecycle costs or when independent authority/recovery checks fail.

## Lightweight delivery and promotion gate

For B8/R1/O1, record each advertised hardware profile: OS, CPU, RAM, accelerator/VRAM or CPU-only mode, storage, model/runtime revisions, quantization and enabled roles. Keep one baseline; enable browser/OCR, graph/vector, rerank and draft-model workers only when a capability needs them. Loading everything at startup defeats on-demand delivery. No invented megabyte ceiling or claim of universal hardware support is justified by these sources.

| Measurement    | Required boundary                                                                                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Installation   | Host package, native libraries, model weights/tokenizers and optional assets separately; download and installed bytes, licenses and preparation method.                                |
| Startup        | Fresh installation/prepared assets, process-cold/model-cold/cache-cold and warm start separately; time to usable Pi task, not merely listening port.                                   |
| Idle and peak  | RSS/CPU, accelerator allocation, disk/write amplification, process count and optional-worker residency; host and model service separately.                                             |
| Task lifecycle | Queue, prefill/decode, tools, extraction/indexing, verification, retries, deletion/rebuild/restore and offline improvement; tokens and observed monetary/energy costs where available. |
| User outcome   | Verified completion, correctness, evidence sufficiency, malformed tools, abstention, recovery and p50/p95/p99 completion latency; missing samples/costs remain unknown.                |

Preregister workloads, paired sample units, quality floor, resource budgets, confidence method and stopping rule in the [qualification register](../design/qualification-register.md). Freeze source/model/runtime contracts for each comparison. Include empty-context restart, cold cache, no-network operation, unavailable local roles and zero-egress checks for every enabled role. Prepared offline assets and first-ever installation are distinct cases: document the supported preparation path rather than pretending absent weights can load offline.

Promote only after hard authority, deletion, durability and zero-egress gates pass; the registered quality floor holds; and the claimed task-level improvement fits that profile's total lifecycle budget with reported uncertainty. Reconcile with the memory review's stricter route-specific gates rather than replacing them. Record failures, negative results and incomplete runs. A throughput win on saturated serving, a warm TTFT win, a smaller packet or a publisher score alone cannot establish faster, lighter, equal-quality Splyce.

No model, executor, worker or inference cache was run for this review. Installed-platform behavior, energy, quality and end-to-end savings remain unmeasured.
