# Cross-session memory: a narrow research frontier

**Active product scope:** Splyce keeps agent execution, memory, and stored state local. Each inference role may use a local runtime or an explicitly authorized cloud API profile with recorded endpoint, model/revision, and egress scope; it never silently switches provider or falls back. Hosted memory and executors below remain comparative research, not product dependencies. [Current master plan](../../../MASTER-PLAN.md).

**Research date:** 2026-10-25. **Method:** selected primary documentation, upstream repositories, and papers; no candidate was installed, connected to a real memory store, or benchmarked locally. Therefore every proposed design and local-gain statement is **n=0**. This is a bounded frontier, not an exhaustive market survey and not a claim that any system is "best."

The later [pinned memory mechanism review](memory-mechanism-review.md) follows selected implementations beyond this overview. Its source-specific findings and counterevidence govern any conflicting mechanism assumptions; neither chapter is runtime qualification.

## What makes claude-mem unusually token-efficient

[claude-mem](https://github.com/thedotmack/claude-mem) has the clearest documented interaction contract for an agent harness. Hooks capture tool activity and the worker turns it into observations; session-start context exposes a compact index, while a stop-hook can produce an end-of-session summary. Its documented retrieval contract is deliberately three-stage: `search` returns a small ID/title/date/type index, `timeline` gives bounded temporal neighbours, and `get_observations` fetches full narratives, facts, files, and concepts only for selected IDs. The repository describes a local worker, SQLite/FTS5 as memory content, Chroma as a semantic-search projection, and an MCP-to-HTTP path. A raw-tool-I/O disclosure exists as a last resort after the observation path. This separation of receipts, compact index, and expansion is the strongest directly reusable mechanism; the repository's token figures are vendor documentation, not independently reproduced measurements.

Its recovery and scope model is useful but should not be over-read. Project filters occur on retrieval; `/clear` starts a new prompt context while retaining a continued session and reinjecting recent memory. The configuration documents a recency window that can exclude old results unless disabled, an observer/summary opt-out for short headless work, and a localhost worker default. It also says source files and original transcript/raw material may be reached on demand. These are recoverability building blocks, but the fetched documentation does **not** establish a complete secure-deletion proof, tenant authorization model, retention policy, or an independently audited cross-workspace isolation guarantee. A native design should therefore make workspace IDs authorization boundaries, retain deletion tombstones and dependency edges, and verify projection removal rather than assuming that deleting a summary removes its embeddings or derived claims.

## Comparable memory mechanics

[Mem0](https://docs.mem0.ai/open-source/overview) distinguishes a self-hosted/open-source library or server from its authenticated hosted Platform API. The official OSS REST reference exposes create, search, update, item deletion, identifier-scoped deletion, and per-memory history; its documentation explicitly says hosted `/v1/` paths do not apply to the OSS server. That separation is valuable: provider-neutral memory logic can be local while an optional managed control plane has different credentials and lifecycle behavior. The integration lesson is to preserve a backend contract with export, history, filtered deletion, and a testable provider boundary rather than treating “Mem0” as one deployment model.

[Letta](https://docs.letta.com/v1-sdk/memory/memory-blocks) makes a clean architectural split: memory blocks are structured, always-in-context prompt sections, while archival memory is an out-of-context semantic store. The project’s own skills documentation cautions that they are separate systems. This supports a fixed, small working-state prefix plus a tool-mediated archive; it does not prove that every archival result is correct or that block edits preserve provenance. A harness should attach citations and write authority to each block and avoid silently promoting retrieved text into the stable prompt prefix.

[Graphiti](https://github.com/getzep/graphiti) is a different class of system: a temporal graph with episodes, entities, and facts, partitioned by `group_id`. Its MCP source documents bi-temporal fields—when an episode was ingested and when the described event occurred—and validity intervals on facts, so newer information can supersede prior facts while preserving history. That is applicable to changing preferences and project state, but it adds extraction, entity resolution, contradiction, and graph-query cost. The official repository advertises episode deletion, but a correct deletion design still needs a dependency-aware rebuild or invalidation of summaries, embeddings, and derived edges; a graph is not a deletion shortcut.

[HippoRAG](https://arxiv.org/abs/2405.14831) and [HippoRAG 2](https://arxiv.org/abs/2502.14802) are retrieval papers rather than session-memory products. They combine a fact/passage graph with Personalized PageRank; the second paper adds deeper passage integration and online LLM use. Their “hippocampal” language should be treated as an algorithmic metaphor only. The reusable hypothesis is typed, provenance-preserving edges (receipt→observation→summary→claim) plus graph diffusion as one candidate ranker. It does not justify biological persistence, and it should compete against sparse lexical search and a simple recency baseline in the target workload.

[A-MEM](https://arxiv.org/abs/2502.12110) proposes agentic organization of memory using Zettelkasten-like structured notes and dynamic links. [MemOS](https://arxiv.org/abs/2505.22101) proposes treating memory as a managed system resource; its active implementation has a substantially broader product scope than a minimal harness. [MemU](https://github.com/NevaMind-AI/memU) describes a compact, agent-driven Markdown/wiki approach: host adapters capture sessions, agents choose retained material, and the backend indexes it for search. These are three viable directions—linked notes, managed tiers, and inspectable files—but only the last naturally exposes user-editable artifacts. None of their reported capabilities establishes local gains here.

[Cognee](https://www.cognee.ai/how-cognee-builds-ai-memory) describes an extract–cognify–load pipeline that builds graph and vector representations, while [EverMemOS](https://arxiv.org/abs/2601.02163) describes MemCells, thematic MemScenes, consolidation, and reconstructive recall. Both motivate consolidation as a separate, reviewable job rather than online mutation of all remembered state. [Supermemory](https://api.supermemory.ai/v4/reference) and [Hindsight](https://github.com/hindsight-ai/hindsight-ai) provide managed/API-oriented alternatives with explicit memory/document lifecycle APIs or an MCP bridge. They can inform adapter design, but managed retention, account boundaries, and deletion semantics must be verified against the chosen service contract before any use.

[MemoryOS](https://github.com/BAI-LAB/MemoryOS), `MEM-memoryos-paper-code`, is the canonical implementation linked by the Memory OS of AI Agent paper. It is separate from MemOS and other same-name products. Its hierarchical storage, updating, retrieval and generation modules and MCP integration are useful comparison inputs. Its published personalization/LoCoMo results do not establish coding-task recovery, cross-workspace isolation or deletion guarantees. Compare lifecycle behavior and full extraction/retrieval cost under M1/M2 before choosing any component; no bundled second generation loop is adopted.

## Identity corrections and non-matches

**Absolute Zero / Absolute Zero Reasoner** is not an episodic-memory system in the primary paper. [AZR](https://arxiv.org/abs/2505.03335) is a zero-data, reinforced self-play reasoning method: a model proposes code-based reasoning tasks, a code executor validates tasks and answers, and the resulting reward guides training. Exact-name public-primary searches did not establish a separate canonical AI-memory product called “AbsoluteZero”; similarly named repositories are unrelated or non-primary for this question. AZR may inform test-curriculum generation for a memory evaluator, but it is not evidence for cross-session storage or retrieval.

**GraphLang** has at least one real, independent upstream identity: [carloscdias/graphlang](https://github.com/carloscdias/graphlang) is a DOT-inspired DSL which compiles LLM-agent graphs into a LangGraph structure. It is an orchestration language, not a cross-session-memory product, and must not be renamed to or confused with LangGraph. **GraphSmith** has multiple independent exact-name candidates: [SathiaAI/graphsmith](https://github.com/SathiaAI/graphsmith) is an agent skill/scaffold focused on crash recovery and replay verification; [jonaselgammal/Graphsmith](https://github.com/jonaselgammal/Graphsmith) is a typed graph planning/runtime and skill-registry project. Neither is LangSmith, and neither was selected as memory evidence. **OMEGA** is no longer ambiguous at the organization/repository level: [omega-memory/omega](https://github.com/omega-memory/omega) is an independently maintained local-first coding-agent memory project, documenting SQLite memory/edges/embeddings, MCP tools, hooks, timeline, backup, compact/consolidate, and a search pipeline. Its public README makes product claims but does not establish independent performance, isolation, or deletion guarantees. Do not design against a presumed “GraphLang/GraphSmith memory” API without an exact upstream URL and scope.

## Proposed native pipeline (design, not implementation)

**Reuse decision for the Pi foundation:** evaluate OMP's [Mnemopi memory package](https://github.com/can1357/oh-my-pi/blob/main/packages/mnemopi/README.md) behind the common memory contract. Its SQLite/bank facade and optional local ONNX/model services; its remote options are not adopted make it a concrete integration candidate. Host scope, provenance, deletion and backup guarantees still need qualification. Native Splyce memory does not require a new memory engine; prefer an existing backend that passes the same tests with less maintained code. [Foundation comparison](../foundations/pi-foundation.md).

1. **Capture receipts and artifacts.** Write immutable, minimally redacted event receipts for user turns, tool calls, file/version references, outputs, failures, and authorization scope. Keep raw artifacts addressable behind receipt IDs; never use a generated summary as the only record.
2. **Summarize and index asynchronously.** A bounded summarizer emits typed observations and one task/session summary, each with cited receipt IDs, source workspace/project/session/task IDs, confidence, creation time, and supersession links. Build sparse text, vector, and optional graph projections as derived data.
3. **Retrieve by progressive disclosure.** Start with a stable cached prompt prefix containing system policy plus tiny active-task state. Query returns an index with IDs, scope, time, provenance, and estimated token cost; then expand a bounded timeline/graph neighbourhood; only then fetch cited evidence or raw artifacts. Enforce a token budget and stop expansion when evidence is sufficient.
4. **Use evidence explicitly.** The runtime passes only selected evidence to the model and records which IDs informed the answer or action. Claims without receipts remain tentative. This makes later correction and recall measurable.
5. **Compact, recover, and delete.** Compaction creates a new cited layer; it never overwrites earlier receipts. Recovery begins from the project/task index and expands by ID. Deletion is a scoped request that records a tombstone, removes/blocks raw content, summaries, embeddings, and graph edges, then rebuilds affected aggregates; every retrieval path must reject tombstoned sources.

Scopes should be hierarchical—organization (if any), workspace/project, task, session, and user—with default retrieval confined to the active workspace and task. Cross-workspace recall needs an explicit grant and a returned provenance marker. The stable prompt prefix should change slowly to maximize provider prompt-cache reuse; volatile retrieved evidence belongs after it. “Neural” or “hippocampal” graph ideas become testable typed retrieval alternatives, never a claim of biological memory.

## One owner, explicit model profiles

The unified CLI/app should own the receipt log, access policy, lifecycle, and retrieval experiment registry. Providers are replaceable role adapters, never nested autonomous memory stacks. A role contract must persist: `role`, provider/endpoint, immutable model revision, tokenizer or documented tokenization behavior, context/input limit, batch limit, request/response schema, usage fields, vector dimension, distance metric, normalization state, query/document instruction or task type, and failure/retry policy. Every derived vector records the exact embedding contract and source receipt hash. A changed embedding model, revision, dimension, normalization, tokenizer, or query/document instruction creates a new index generation and forces reindexing before mixed comparisons; it must not be silently mixed with old vectors.

Raw artifacts, derived stores, and memory lifecycle remain local. Generation, extraction, embeddings, and reranking each use a recorded local or explicitly authorized cloud profile with least egress needed for that operation. A failed/missing role cannot select another provider as fallback. Secrets stay outside receipts; every profile needs scope checks, tombstones, exports, recovery tests, and actual capability evidence. Provider APIs below are sources, not qualified runtime support.

Provider facts illustrate why the contract must be explicit. Nomic exposes task type, output dimensionality, long-text handling, and local/remote/dynamic inference modes. Jina exposes separate embeddings and rerank endpoints, optional normalized vectors, task selection, and dimensionality where supported. Gemini documents embedding dimensions, task types, token limits, usage metadata, and an incompatible embedding-space change between `gemini-embedding-001` and `gemini-embedding-2`; that is a concrete reindex trigger. Cohere documents reranking as a distinct endpoint and limits/constraints for candidate ranking. Model cards and APIs can change, so these are discovery candidates, not pinned defaults.

## Retrieval experiment, not a fixed stack

Run every configuration under the same memory owner and corpus snapshot. The initial ablation grid is: BM25 only; dense only; BM25+dense with Reciprocal Rank Fusion (RRF); each of those with a reranker; and graph-route retrieval that may add bounded receipt/observation/claim neighbourhood candidates before the same fusion/rerank stage. A graph route must expose why each edge was followed and remain optional; HippoRAG-style PPR is one contender, not a presumed winner. Evaluate exact raw-artifact retrieval separately from summary retrieval to catch summary-induced loss. Keep candidate IDs and source citations through fusion and reranking so an answer can prove which original receipt supported it.

## Graph and learned-memory boundaries

Knowledge graphs model entities and facts; workflow graphs model execution dependencies; code graphs model program structure; none is automatically a learned graph retriever. [G-Retriever](https://arxiv.org/abs/2402.07630) is a GNN+LLM RAG method for textual-graph question answering, with trainable GNN graph encoding/soft prompting. [GRAG](https://arxiv.org/abs/2405.16506) is graph retrieval-augmented generation. Both are different from receipt/provenance graphs and should only enter as separately measured retrieval routes. A citation edge or task DAG is useful for audit even when no GNN runs.

Likewise, learned test-time memory is distinct from external cross-session storage. [Titans](https://arxiv.org/abs/2501.00663) introduces a neural long-term-memory module updated during inference; [MIRAS](https://arxiv.org/abs/2504.13173) is a framework for associative memory, attentional-bias objective, retention gate, and memory-learning algorithm. These are model-architecture research, not drop-in deletion-capable stores. HippoRAG remains an external hippocampal-_inspired_ graph-retrieval method, not evidence that a system has learned neural memory or biological properties. The native system may compare these paradigms later, but has no runtime results.

[LongMemEval](https://arxiv.org/abs/2410.10813) assesses information extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention; [LoCoMo](https://github.com/snap-research/LoCoMo) provides long multi-session conversational memory tasks. They are useful evaluation inputs, but neither proves coding-harness recovery, deletion propagation, workspace isolation, or cost/latency. [MemoryBank](https://arxiv.org/abs/2305.10250) is relevant prior external-memory work, but it does not change the receipt-first proposal above. No runtime results were produced in this research.

## Evaluation contract before choosing a design

Compare against (a) no cross-session memory, (b) compact hand-authored project/task summaries, and (c) lexical receipt search. Record per task: injected and total tokens, model/provider cost, retrieval and end-to-end p95 latency, held-out recall and evidence-use precision, correction rate, and deletion/isolation failures. Report these separately by scope and corpus size; there are no local measurements yet.

Concrete acceptance tests:

1. A deleted receipt is absent from lexical, vector, graph, summary, timeline, export, and cached retrieval results after rebuild, while an audit tombstone remains.
2. Two workspaces with identical entity names cannot retrieve each other’s receipts, summaries, or embeddings without an explicit grant.
3. A stale summary that contradicts a newer cited receipt is down-ranked or flagged, and the answer exposes the newer receipt ID.
4. Starting from an empty model context recovers a held-out completed task through index → timeline → evidence expansion within a declared token budget.
5. Removing the summary/index pipeline causes a measurable failure in the held-out evidence-use assertion; a test may not pass merely because a model guessed correctly.

## Risks

- Generated observations, links, and graph edges can amplify incorrect or stale input; provenance must survive every derivative.
- Vector/graph projections raise deletion, leakage, latency, and model-call costs relative to a receipt index.
- Tool-provider claims and paper-reported benchmarks do not transfer to a coding-harness workload; all target gains remain n=0.
- Search naming collisions are material: integrating a similarly named repository without canonical provenance can silently substitute a different system.
