# Platform, security, and release contracts

**Pi-first applicability:** Pi is the selected existing engine. Rust crate examples below are optional support-component candidates, not instructions to replace its loop, clients, MCP or process handling. Reuse and qualify Pi’s actual path first. [Foundation decision](../foundations/pi-foundation.md).

This is an implementation-gap handoff, not a claim that Splyce has any of these controls. Rust gives memory safety for safe Rust and portable APIs; it does not own a child process after spawning it, make a filesystem durable, grant a sandbox, protect a secret, authenticate a remote server, or prove a release artifact. Those are explicit platform contracts to test on each shipped target.

| Native executor isolation               | Use OS guarantees where available: Landlock can restrict a process and future children; App Sandbox/AppContainer are different product and entitlement models. Verify ungranted host calls are rejected.                                       |
| Remote MCP authority                    | Treat remote MCP as a separate principal: bind tokens to the intended resource/server, validate discovery metadata and redirect policy, keep local tool authority separate, and give remote servers least privilege. OAuth success does not grant local shell or workspace access.                                             | [MCP Authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)                                                                                                                                               | A remote connection records endpoint identity, scopes, token reference, and approved tool policy. It cannot inherit local executor or keyring authority.                                                                                    | A test server receives a token for its resource and permitted tool call; a mismatched resource, scope, endpoint, or local-only tool invocation is rejected with an auditable decision.                                                                 |
| Signed updates and releasable artifacts | Release only immutable versioned artifacts with checksums, SBOM, provenance attestation, and a verification step before install/update. Pin workflow actions and build tooling by immutable revision. `cargo-dist` is a packaging candidate; generated automation is not supply-chain proof.                                   | [GitHub artifact attestations](https://docs.github.com/en/enterprise-cloud%40latest/actions/concepts/security/artifact-attestations)                                                                                                            | Update manifest binds version, target, artifact hash, SBOM, provenance and minimum updater version. The updater verifies before replacement and retains the previous binary until health check succeeds.                                    | Build a release fixture for every target; verify provenance and SBOM against its exact artifact, reject a changed byte and an unpinned action, then test successful update and rollback after a failed health check.                                   |
| Dependency and licence gate             | Lock dependencies and gate the resolved graph with `cargo-deny` (licenses, bans, advisories, sources) and `cargo-audit` on the lockfile. The release job uses the committed lockfile.                                                                                 | Introduce a fixture policy violation for each gate class and assert CI rejects it; restore the lockfile and assert the release job reports the resolved graph used to build the artifact.                                                              |

## Guarantees and untested boundaries

Safe Rust reduces memory-unsafety in Splyce code; Tokio coordinates async work; SQLite implements its documented database protocol; and Wasmtime isolates a guest according to the configured imports. None establishes cross-platform PTY fidelity, process-tree completion, disk persistence after a failure, OS sandbox availability, credential-store availability, remote-service identity, or release provenance for a particular build.

The referenced OS services provide only their documented, platform-specific mechanisms. Splyce therefore needs a capability report and the acceptance tests above on every release target. As of this research snapshot, **all Splyce contracts and tests in this chapter are untested proposals**; no candidate crate, OS sandbox, MCP server, credential store, database migration, installer, or release workflow was installed or exercised.
