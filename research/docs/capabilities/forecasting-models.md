# Forecasting models: Timestral and local workload prediction

Reviewed **2026-10-25**. Public-source research, selected pinned source inspection and proposed experiments only. Splyce forecasting and scheduler results are **n=0**. [Source ledger](../evidence/forecasting-sources.json). Optional B8 research connects to [efficiency](efficiency-and-recursive-improvement.md), [qualification](../design/qualification-register.md) and the [master plan](../../../MASTER-PLAN.md).

## Scope and first decision

A forecast predicts numeric observations over time. It does not establish whether an agent has completed a task, whether a tool is permitted, or whether a generated claim is true. Candidate uses are measured queue/workload volume, latency, memory/CPU/VRAM demand or local model-loading demand, where sufficient history and a concrete scheduling decision exist. A single irregular desktop task may have neither repeatable seasonality nor enough data; in that case no forecaster is the appropriate baseline.

Start with last-value, seasonal-naive and EWMA predictions plus existing conservative resource limits. Compare a small fitted linear/classical model before adding neural weights. Forecasts may advise Splyce's local operational scheduler while Pi retains its turn loop; they cannot change grants, correctness requirements, deadlines or cancellation semantics. Forecast inference uses a recorded local or explicitly authorized cloud profile; memory and state remain local, and no provider fallback is permitted. Optional workers start only on explicit enabled demand. Recommended/default adoption must earn its full resource burden; a compatible user-selected experimental model can run with quality/performance labeled unmeasured.

## Chain 1: identify official Timestral, then separate code and weights rights

**Primary identity → mechanism:** [Mistral's launch, FOR-01](https://mistral.ai/news/timestral/) names Timestral sizes 5M, 28M, 123M and 209M. The official [repository, FOR-02](https://github.com/mistralai/timestral/tree/a534bdbd244d64f3d9d743f46c7bf6fc330ed4ff) supplies standalone CPU/GPU inference with PyTorch, NumPy, safetensors and huggingface_hub. [Official 28M documentation, FOR-03](https://docs.mistral.ai/models/timestral-1-0-28m) documents up to 32K timesteps, past-only/known-future covariates and probabilistic quantile outputs. Unrelated sites or similarly named ports cannot establish official authorship, architecture or rights.

**License chain → hard admission limit:** the actual [code LICENSE, FOR-04](https://github.com/mistralai/timestral/blob/a534bdbd244d64f3d9d743f46c7bf6fc330ed4ff/LICENSE) is Apache-2.0. The separate pinned [28M weights LICENSE, FOR-05](https://huggingface.co/mistralai/Timestral-28M/blob/49b26409ac87b5935539a5d8ffe7f397b720db47/LICENSE) is Modified MIT and withholds rights when the company/employer's global consolidated monthly revenue exceeds USD 20 million for the preceding month. This is a substantive restriction: do not label these weights ordinary MIT, unrestricted OSS or automatically distributable with Splyce. Other sizes need their own exact-file review. These weights remain outside the unrestricted OSS default/distributed asset set. Users whose intended use is permitted may independently install/select Timestral through a compatible local forecast adapter, as specified in [user-controlled models](../design/user-controlled-models.md); this does not relicense or bundle those weights. Separately negotiated permission needs its own scope and still does not establish unrestricted OSS weights. Experimental user selection needs compatibility/locality/lifecycle admission; recommendation/default promotion additionally needs the comparative quality/resource gate below.

**Local burden → falsifiable use:** upstream lists weight files around 21/111/490/837 MB; these exclude Python/PyTorch, caches, activations, startup and packaging. An offline local-path loader is useful, but does not remove weight restrictions or prove Windows/CPU cost. Reject admission if licensing is incompatible even if forecast scores improve. A hosted Mistral endpoint is a separately unqualified cloud profile; it does not substitute for local scheduler/state ownership or authorize hosted training.

## Chain 2: probabilistic architecture does not guarantee calibrated long-horizon uncertainty

**Source-observed mechanism:** [pinned model, FOR-06](https://github.com/mistralai/timestral/blob/a534bdbd244d64f3d9d743f46c7bf6fc330ed4ff/src/timestral/model.py) embeds value/missingness patches, applies causal context normalization and uses learned forecast-query tokens. Its quantile head constructs non-crossing quantiles. The [pinned forecaster, FOR-07](https://github.com/mistralai/timestral/blob/a534bdbd244d64f3d9d743f46c7bf6fc330ed4ff/src/timestral/forecaster.py) feeds medians back between forecast blocks and separates target, past-only and known-future covariates. This is source inspection, not numerical verification.

**Limit → mitigation:** non-crossing quantiles are an ordering property, not evidence of nominal coverage. Feeding median predictions into later blocks may compound bias and omit uncertainty from alternative paths; this is a testable risk, not a measured defect. The same source applies forecast refinement/capping, so compare actual exported defaults and horizon behavior rather than an abstract transformer. Evaluate per-horizon coverage, interval width, tail misses and proper scores across quiet periods, bursts and structural changes. Test multiblock horizons separately from short direct predictions; a short-horizon publisher score cannot qualify both.

**Splyce use → decisive rejection:** a predicted p95 memory demand could advise whether to defer optional indexing, never whether to omit required verification. Reject if intervals miss registered coverage, bursts exceed safe headroom, or a better average score worsens deadline/quality outcomes. Keep actual scheduler resource limits authoritative and provide a measured simple fallback when history/model availability is insufficient.

## Chain 3: covariates create a future-information boundary

**Mechanism → failure condition:** known-future covariates can improve forecasting only when they were actually known at the prediction origin. A planned local batch schedule qualifies; subsequently observed demand or latency does not. Causal attention inside a model cannot repair a dataset that exposes later labels, globally fitted scalers or retrospectively revised inputs.

**Mitigation → contract:** bind every forecast to `asOf`, observation timestamps, ingestion/version timestamps, series identity, frequency, timezone, units, horizon, missingness, model revision and covariate availability. Preserve event time and availability time separately. Use time-ordered rolling-origin splits; fit normalization, imputation, features, calibration and model selection using eligible training history only. Never random-split overlapping windows from one trajectory across train/test. Pin data revisions and keep later backfills out of earlier snapshots. Daylight-saving transitions, irregular samples, missing/duplicate points, newly created series, cold starts and scale changes are explicit fixtures.

**Splyce use → decisive rejection:** resource predictions are provisional artifacts with their generation time and expiry. An old forecast cannot authorize present work. Inject later observations and assert earlier forecast inputs remain byte-identical. Reject any candidate whose gain disappears under this as-of reconstruction or whose covariate requirements cannot be met locally at dispatch time.

## Qualification and integration contract

| Experiment | Frozen comparison and fixture                                                                                                     | Promotion and rejection evidence                                                                                                                                                                                                                                                      |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FOR-A      | Recorded local traces with rolling origins; last-value, seasonal-naive, EWMA, small fitted model and one neural challenger        | MAE/MASE where defined, quantile pinball/WIS, coverage and width by horizon/workload; record zero-scale denominators and missing metrics honestly. Reject no reliable gain at registered quality/resource limits.                                                                     |
| FOR-B      | As-of snapshots, known-future calendar/schedule covariates, later backfills, missing intervals, outliers, bursts and drift        | Prove no future leakage, units/frequency correctness and visible insufficient-history behavior. Keep final holdout untouched after selection.                                                                                                                                         |
| FOR-C      | Cold/warm load, offline empty-cache failure, local prepared assets, concurrent generation, cancellation and worker crash          | Measure full dependency/download bytes, cold/warm/p95/p99, idle/peak RSS/VRAM, CPU/disk/energy if measurable and cleanup. Failed asset loading cannot invoke hosted inference.                                                                                                        |
| FOR-D      | Loaded Pi task trace replay, unchanged scheduler versus forecast-advised scheduling under identical arrivals/resource constraints | Compare completion latency, throughput, deadline misses, verification/task quality, peak resources and forecast overhead; include a no-forecast arm. Replay assumptions must be checked in a later live local trial. Reject forecast-score wins without useful scheduler improvement. |

Choose independent sampling units (for example host-days or sessions), report paired uncertainty and preserve failures/cancellations. Fix budgets, quality floor, forecast horizon and stopping rule before runs. Scheduling changes affect later observations: replay is counterfactual under declared assumptions, not proof of causality or live performance. Count forecasting, feature collection, storage, retraining/calibration, reloads and contention with the agent in total cost. Store model/data revision, exact commands, observed outputs and final code revision in the qualification record only when run. Drift, changed workload, model/quantization revision or broken interval coverage reopens the decision.
