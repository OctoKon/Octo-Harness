# Cloud request retention, cancellation and lifecycle

**Reviewed 2026-10-26; public documentation only, provider calls/account verification n=0.** This closes the missing documentary map for cloud lifecycle in [API conformance](provider-api-conformance.md) and [profiles](../design/providers-profiles-and-sessions.md). [CLD-01–08](../evidence/cloud-lifecycle-sources.json) record the sources. A local application/store does not imply local inference, remote deletion or cancellation. Provider/model/API/account arrangements are separate qualification cells.

| Provider/API                           | Source-backed distinction                                                                                                                                                                                            | Splyce admission and truthful result                                                                                                                                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenAI / CLD-01                        | Official data controls distinguish abuse-monitoring logs from application state; retention eligibility depends on endpoint, feature and arrangement. `store: false` does not establish every kind of zero retention. | Record exact endpoint/features and account evidence; do not infer ZDR from a request flag or local transcript. Default off for server-side files/conversations unless separately selected.                                 |
| OpenAI Responses cancellation / CLD-02 | The documented cancel endpoint applies to responses created with `background: true`.                                                                                                                                 | Foreground transport abort is not that acknowledgement; background mode requires separate permission/state/retention qualification. Never enable background storage solely to make cancel look stronger.                   |
| Anthropic / CLD-03–04                  | Current platform docs distinguish processor/platform, eligible features and Covered Models; the privacy article separately gives a standard retention timeframe with exceptions.                                     | Do not merge these into one universal TTL. Bind the model, processor, feature and applicable arrangement/source date; unresolved account applicability is explicit and blocks a data class demanding a stronger guarantee. |
| Gemini / CLD-05–06                     | Abuse monitoring and developer project logging/datasets are different storage paths; logging/dataset choices have separate retention behavior.                                                                       | Paid/unpaid/account/project and selected API features need their own record; disabling a visible log does not prove all service copies erased. No dataset-sharing opt-in follows from model selection.                     |
| Amazon Bedrock / CLD-07                | Current retention modes, model requirements and processing region matter; source documents model-dependent safety review and rejection when a strict retention mode is incompatible.                                 | Bind actual API route/model/account/project/region policy. | Azure Foundry / CLD-08                 | Microsoft distinguishes data processing, feature storage and monitoring for models sold by Azure; its processor/arrangement differs from a first-party OpenAI account.                                               | Qualify the actual deployment and service controls. A compatible Responses payload does not transfer OpenAI account retention or cancellation guarantees.                                                                  |

These selected policies do not qualify every compatible third-party host or private agreement. A custom endpoint needs its own evidence; a protocol name cannot manufacture it. Outside the documented OpenAI background operation, remote cancellation acknowledgement is not established by this review. Record it as unsupported/unknown until the exact provider operation establishes otherwise, rather than inferring absence or success.

## Required per-cell record and tests

For each advertised role record provider/processor/API/model/deployment/account-region references; allowed data classes; policy source/date and account arrangement; request `store`/cache/file/background features actually used; server cancellation operation and acknowledgement semantics; remote object IDs/deletion or expiry limits; and exact opt-in test receipt. No secrets or raw private request content belongs in a public qualification record. Policy changes, mutable aliases, endpoints/features and account arrangements reopen qualification.

Represent cancellation as **local stopped**, **remote acknowledgement observed**, **remote acknowledgement unsupported**, or **unknown**, with separate local cleanup and usage state. A socket close, GUI cancel button or SDK exception cannot imply zero charge, erased inputs or undone tool effects. Represent local deletion separately from provider-controlled retention; if a requested guarantee cannot be met, deny that data class/feature or report the unresolved external copy rather than issuing a complete-erasure receipt.

Proposed cases `C4_cloud_retention_policy`, `C4_cancel_ack`, `C4_remote_object_lifecycle` and `C4_account_change` cover: incompatible strict-policy refusal; transport abort without remote acknowledgement; changed arrangement/endpoint; explicit upload/delete/expiry; unknown usage after disconnect; and no automatic alternate provider. Use synthetic transports for deterministic faults, then authorized exact-provider/account cells for advertised operation. Basic inference can qualify with accurately disclosed retention/cancel limits when the user's data policy permits them; a universal remote-erasure capability is not invented as an admission prerequisite.

Ownership is Itachi's native egress/authority gate TD-14/50, actual-provider qualification TD-52, and the lead-reviewed GUI support/cancel states. No provider API was called and no account control was changed in this research.
