## Branch flow and automated promotion

**Status: applied 2026-10-26.** This line is the activation signal that AGENTS and CONTRIBUTING use. Live rulesets: Protect staging (25846046), Staging merge permissions (25846047), Protect main (25824256) and Main update permissions (25829116, updated in place on 2026-10-26 so the release app is its only bypass actor). `promote.yml` fast-forwards `main` to each fully green staging commit; `main` holds only commits that passed the full staging gate, nobody opens a PR against `main`, and no person can update it.

1. **Develop** on `<GitHub-username>/<short-scope>` (or a declared multi-owner integration branch). Local commits and pushes there are work-in-progress, not publication.
2. **PR to `staging`** once applicable local checks/E2E pass. [Protect staging](../../../.github/rulesets/staging.json) requires a PR, squash merge and passing `Documentation quality`, `Analyze Python`, `Analyze Actions` and `Staging release gate`, with **no approval**: automated checks replace human review. [Staging merge permissions](../../../.github/rulesets/staging-updates.json) lets only `Itachi-1824` and `MdSiddiqx` merge, and only through a PR, so their merges still satisfy every check. Merging is manual and requires the PR branch to be up to date with `staging`, so checks always ran on the exact combination that lands. A merge queue was tried during activation on 2026-10-26 and removed: GitHub performs queued merges itself, which the leads-only update restriction rejects (`Cannot update this protected ref`), and limiting merges to the two leads takes precedence. The PR dependency review runs inside `Documentation quality`. Head branches are deleted automatically after merge.
3. **Staging gate.** Every push to `staging` reruns those checks and the [Staging release gate](../../../.github/workflows/staging-gate.yml) on a Windows runner. The same gate also runs on every PR to `staging` and is a required `staging` check, so a failing runtime suite cannot land there. Once `npm run test:release-gate` is defined it always runs; before then the job fails if runtime source exists under `apps/`, `packages/` or `vendor/` (UI prototypes under `apps/desktop/prototype/` excepted) and otherwise records runtime E2E as N/A. GitHub's `windows-latest` runner is Windows Server 2025: it builds and runs integration checks but never qualifies a Windows 11 support cell. Windows 11 cells, including Microsoft Execution Containers qualification, need a Windows 11 environment with artifact-bound receipts: GitHub's hosted `windows-11-arm` runner for an Arm64 cell, or a self-hosted Windows 11 x64 runner that only runs on trusted `staging` pushes and manual dispatch, never on pull requests from forks. A self-hosted runner must be a dedicated, disposable Windows 11 environment registered for one job at a time (just-in-time or ephemeral), reset externally after every job including interrupted ones, with minimal credentials and no signing or promotion keys; receipts name the clean image used (`R1_runner_reset`: a first job leaves a file outside the checkout and a background process, and the next qualification job starts without either). See GitHub's [self-hosted runner hardening](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners). TD-01 creates that script with its first source (initially the contracts suite), TD-11 extends it with every engine/GUI runner it adds, and TD-80 completes it as the full runtime suite (type/build/integration, packaged Windows E2E and the release-smoke subset), so promotion never stalls waiting for TD-80.
4. **Promotion.** [Promote staging to main](../../../.github/workflows/promote.yml) runs when any of those workflows completes on a staging push. Using a short-lived GitHub App token, it fast-forwards `main` to that exact commit only when the commit is on `staging`, `main` is its ancestor, and all four required GitHub Actions check runs on that SHA succeeded. A pending check exits without action; the next completion retries. Promotion may advance `main` to any fully checked staging commit that is a fast-forward of `main`, even if a later staging commit is still running or has failed; it never promotes a commit lacking all four green checks. Only one promotion run waits at a time; a manually dispatched gate rerun also triggers promotion. The released SHA is therefore byte-identical to the tested one; no merge or squash recreates it.
5. **Release artifacts.** Tags, GitHub Releases, SBOMs and artifact attestations are added to the promotion path by TD-58/80 once packaged binaries exist, with a tag ruleset restricting `v*` to the release app. Nothing is published as a release before then.

[Protect main](../../../.github/rulesets/main.json) keeps deletion, force-push and linear-history protection and requires the four checks on any commit entering `main`. [Main update permissions](../../../.github/rulesets/main-updates.json) restricts updates to the release app `octokon` (app ID 5476745) as its only bypass actor. Changing rulesets remains an explicit administrator action.

**Historical observation before activation, 2026-10-26:** ruleset 25824256 "Protect main" matched the earlier PR-based policy. A second active ruleset, 25829116 "Main update permissions", restricts updates to `main` with bypass for `Itachi-1824` (always) and `MdSiddiqx` (pull requests only). It was created 2026-10-25 and was not recorded here before. Once the release app exists, `main-updates.json` replaces both human bypasses with it. Until then ruleset 25829116 stays as the interim (it still lets MdSiddiqx merge a PR into `main`, so the Itachi-only rule is a policy, not a technical lock), and by policy only Itachi-1824 performs promotions, each a fast-forward of a staging commit with all four required checks green; Protect main (25824256) still enforces fast-forward and those checks on every update.

### Free security and quality controls

| Control                                               | Status                                                           | Scope                                                                                                                                                                                                                                            |
| ----------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Secret scanning and push protection                   | Enabled (live read-back)                                         | Blocks recognized secrets at push; free for public repositories                                                                                                                                                                                  |
| Dependabot alerts and security updates                | Enabled (live read-back)                                         | Security-update PRs target the default branch; retarget them to `staging` before merge                                                                                                                                                           |
| Dependabot version updates                            | Configured to target `staging`                                   | Weekly grouped GitHub Actions and npm tooling                                                                                                                                                                                                    |
| CodeQL `security-extended`                            | Python and GitHub Actions workflows                              | Add `javascript-typescript` and Rust coverage when that source lands                                                                                                                                                                             |
| Dependency review                                     | PRs                                                              | Rejects newly introduced moderate-or-higher vulnerable dependencies                                                                                                                                                                              |
| Pinned actions and least-privilege tokens             | Workflows                                                        | Full SHA pins; read-only default token; promotion uses a scoped, short-lived app token in a branch-limited environment                                                                                                                           |
| Rulesets, environments, GitHub-hosted Windows runners | Free for public repositories                                     | Branch/tag protection, secret scoping, packaged Windows E2E                                                                                                                                                                                      |
| Artifact attestations                                 | Planned with releases (TD-58/80)                                 | Provenance for the signed installer bytes through the public Sigstore instance; provenance only, not a safety claim                                                                                                                              |
| Release SBOM                                          | Planned with releases (TD-80)                                    | The dependency-graph SPDX export does not by itself establish the staged bundle's complete contents, so the release SBOM is generated from lockfiles and the staged bundle (including Node and WebView2 entries) and attached to the attestation |
| Merge queue                                           | Not used                                                         | Incompatible with leads-only merge restriction (see step 2); up-to-date branch checks provide the same base-currency guarantee                                                                                                                   |
| OpenSSF Scorecard                                     | [Weekly and on `main`](../../../.github/workflows/scorecard.yml) | Published supply-chain posture score and code-scanning alerts; advisory, not a merge gate                                                                                                                                                        |

Commercial code-signing certificates cost money, and [EV certificates no longer bypass SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation); on Windows 11, Smart App Control blocks unsigned executables without positive reputation, so an unsigned installer can be blocked outright, not just warned about. The preferred free route is the [SignPath Foundation](https://signpath.org/terms) OSS program: it requires an OSI license, an already released project, CI builds with origin verification, MFA, a published code signing policy and manual approval of every release. Azure Artifact Signing is a paid fallback (individual eligibility limited to the US and Canada). Until signing is in place, every installer is labeled unsigned in its release notes and support labels.

## Known limits

The pinned Markdown toolchain currently reports four low-severity transitive dependency advisories with no offered nonbreaking update. It is development/CI tooling, installed with lifecycle scripts disabled; do not describe that as a clean dependency audit. Dependabot will surface available updates. Project-authored work uses [AGPL-3.0-only](../../../LICENSE), with retained third-party exceptions in [NOTICE.md](../../../NOTICE.md). Public visibility alone does not grant rights to copy third-party implementations.

Pages deployment is called as a reusable workflow only after the required documentation job succeeds on the same main revision; PRs do not deploy. Main workflow runs are not canceled during a valid deployment by a newer push. The PR-only dependency-review step is configured inside the required documentation job. A main-branch push does not exercise that PR event path. Public-repository eligibility is documented by [GitHub dependency review](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-dependency-changes-in-a-pull-request). Partner-pattern validity and extended-metadata checks require Team/Enterprise with Secret Protection; they are not claimed as free enabled controls. [Supported secret patterns](https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns).

## Membership and contribution preflight

Organization membership is separate from effective repository permissions. [GitHub's role table, GV-12](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization) distinguishes upstream push/required-review authority from read/fork contribution. [Public forks, GV-13](https://docs.github.com/en/pull-requests/reference/forks) have their own access controls and remain public. Verify the actor, permitted branch/fork path, target base and eligible reviewer before handoff. The same username naming, privacy, validation and PR gates apply; fork workflows receive no extra token/secrets or policy bypass. A dated roster is planning context, not a standing permission grant. No membership or repository permission is changed by this documentation.
