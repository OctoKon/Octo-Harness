# Evidence research

Use for candidate research, stack selection and architecture claims; skip ordinary implementation work that does not need a literature/product comparison.

1. Read the relevant category index and existing records before searching. Resolve the exact project, owner, fork/successor, version and layer; names alone are not identity.
2. Search to discover current candidates, then fetch a selected public primary source for each decision-relevant claim. Record unavailable sources as unavailable. Do not infer absence of a capability from silence.
3. Write compact mechanism, boundary, reuse hypothesis and acceptance-test notes. Keep vendor/paper results separate from measurements made here. Prefer source-specific claims over marketing superlatives.
4. Add an evidence record with `id`, `tool` (candidate identity), `url`, `title`, `accessed`, nonempty `claims`, `verification` and `notes`. Use the current access date and a direct public primary URL; do not add a private-source inventory.
5. Chain the next round from actual unanswered questions. Deduplicate against the whole corpus, including separately maintained forks and adapters. Record exact queries, new candidates and residual gaps. New findings reset a saturation counter; two zero-new passes establish only the stated query frontier, never global exhaustion.
6. Update `research/README.md`, the category README and any affected catalog/plan links. Run the documentation checks and a privacy review before publication.

For performance decisions, fix the model/revision, workload, environment, quality constraints and budget before paired baseline/candidate tests. Report sample count, errors, latency, cost and limitations. An unrun experiment has no result.
